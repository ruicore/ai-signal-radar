## ① 🆕 AWS：AgentCore 多租户架构，把 agent SaaS 的隔离问题讲清楚了

**Source**：AWS Machine Learning Blog — Shared infrastructure, isolated tenants: Pool model multi-tenancy with Amazon Bedrock AgentCore
**Time**：2026-06-23

### 1. 发生了什么

AWS 发布了一篇非常工程化的 AgentCore 多租户架构文章，核心是用 Tier → Tenant → User 层级管理 agent SaaS：共享底层基础设施，但在文档、memory、model access、工具调用、cost tracking 上保持租户隔离。文章明确目标包括 tenant isolation、service tiers、granular cost attribution。

### 2. 工程上具体做了什么

它不是简单在数据库里加 tenant_id，而是把 tenant context 贯穿整个 agent runtime：

```text
JWT tenant metadata
  → API Gateway tier rate limits
  → Lambda context extraction
  → AgentCore Runtime isolated microVM
  → AgentCore Memory hierarchical namespace
  → AgentCore Identity / Gateway / Policy
  → S3 / KB metadata filtering
  → OpenTelemetry baggage
  → per-tenant cost attribution
```

更关键的是，它用 temporary scoped credentials 和 IAM ABAC 做隔离，而不是只依赖应用层过滤；每个 agent session 运行在 isolated microVM 中，memory 也用 composite actor ID 和 namespace 隔离。

### 3. 为什么重要

这是本周最强的 production agent 架构信号。真正的生产 agent 不是：

```text
LLM + tools.py + vector DB
```

而是：

```text
identity
tenant boundary
runtime isolation
memory isolation
tool authorization
observability
cost attribution
```

AI agent 一旦进入 SaaS / enterprise 场景，最大风险不是“模型答错”，而是 context 泄漏、memory 串租户、工具越权、成本无法归因。

### 4. alternative approach

更强隔离方案是：

```text
tenant-per-stack / tenant-per-account
```

优点是隔离彻底，缺点是成本和运维复杂度高。

更轻方案是：

```text
shared app + tenant_id filtering
```

优点是开发快，缺点是安全边界薄；一旦某个 tool / memory / retrieval 没带 tenant filter，就会出事故。

更现实的中间路线是：

```text
shared infra
+ scoped credentials
+ ABAC
+ namespace isolation
+ trace-level tenant propagation
```

### 5. 对我的启发（可执行）

你自己的 agent backend 里，应该先定义一个不可丢失的 TenantContext：

```python
@dataclass(frozen=True)
class TenantContext:
    org_id: str
    tenant_id: str
    user_id: str
    tier: str
    run_id: str
    allowed_tools: set[str]
    allowed_memory_namespaces: set[str]
    budget_usd: float
```

然后强制每个对象都带它：

```text
AgentRun
AgentStep
ToolCall
MemoryRead
MemoryWrite
ModelCall
TraceSpan
CostRecord
```

如果一个 tool call 没有 TenantContext，默认拒绝执行。

## ② 🆕 OpenAI：Daybreak / Codex Security 把安全 agent 从“发现漏洞”推进到“验证 + patch + disclosure”

**Source**：OpenAI — Daybreak: Tools for securing every organization in the world / Patch the Planet
**Time**：2026-06-22

### 1. 发生了什么

OpenAI 扩展 Daybreak，并发布 Codex Security、GPT-5.5-Cyber、Patch the Planet 等安全方向工具和项目。重点不是单纯做漏洞扫描，而是把 AI-assisted security research 推进到完整防御闭环：发现、验证、严重性评估、patch、测试、披露。Patch the Planet 还与 Trail of Bits 合作，面向 cURL、Go、Python、Sigstore、pyca/cryptography 等开源项目做 AI-assisted security work。

### 2. 工程上具体做了什么

Codex Security 的高信号点在于它强调 evidence-backed findings，而不是 alert spam：

```text
understand codebase / threat model
  → scan full codebase or recent changes
  → find plausible reachable vulnerabilities
  → trace attack paths
  → validate findings
  → produce severity / location / evidence / remediation
  → generate targeted patches
  → verify results
  → export to vuln management / SARIF / CodeQL
```

Patch the Planet 也不是让模型直接给 maintainer 发 PR，而是让安全研究员复现证据、根据文档和 threat model 验证、去重、重新定级，再按 maintainer preference 提交 patch。

### 3. 为什么重要

安全 agent 最容易失败的地方不是“找不到问题”，而是：

```text
误报太多
缺少 reachability evidence
patch 不符合项目风格
没有测试
披露流程混乱
maintainer 不信任
```

OpenAI 这条信号说明：高价值安全 agent 必须从“扫描器”升级为：

```text
validated remediation pipeline
```

也就是 finding + evidence + patch + test + human review + disclosure。

### 4. alternative approach

传统方案：

```text
SAST / CodeQL / dependency scanner
  → issue ticket
  → human triage
  → human patch
```

优点是可控、可审计；缺点是 triage 成本高、漏洞堆积严重。

更激进方案：

```text
agent automatically opens patch PRs
```

速度快，但如果没有 validation gate 和 maintainer-specific constraints，很容易制造噪音。

最稳的路线是：

```text
AI discovery
+ deterministic checks
+ independent validation
+ human approval
+ patch PR
```

### 5. 对我的启发（可执行）

如果你做 security / review agent，输出不要只是文本建议。至少定义：

```python
@dataclass
class SecurityFinding:
    finding_id: str
    file_path: str
    line_range: str
    severity: str
    reachability_evidence: str
    exploit_preconditions: list[str]
    patch_diff: str | None
    tests_added: list[str]
    validator: str
    confidence: float
```

没有 reachability_evidence 和 tests_added 的 finding，默认不允许进入 PR 阶段。

尤其是 code review 这条：GitHub 用通用文件探索工具替换自定义工具，并通过 eval 观察到成本下降，这说明 agent tool surface 的工程化会直接影响 cost-to-completion。

```text
agent runtime
```

```text
ModelProvider
```

其中 AgentUsageMetric 不要只记 token，要记：

```text
mode = completion | chat | agent | review | multi_agent
repo
accepted_diff
merged_pr
review_cost
human_correction_count
```

这比“调用了多少次模型”更接近真实工程价值。

## ④ 🆕 Anthropic：Claude Tag 把 agent 放进 Slack，团队级上下文 / memory / 工具边界成为核心抽象

**Source**：Anthropic — Introducing Claude Tag
**Time**：2026-06-23

### 1. 发生了什么

Anthropic 发布 Claude Tag：团队可以在 Slack 里 @Claude，让 Claude 访问指定 channel、工具、数据和 codebase，完成工程、产品、数据、support 等任务。Anthropic 还提到内部产品团队有大量代码由 Claude Tag 辅助生成，并强调它可以异步执行、跨小时或跨天完成任务。

### 2. 工程上具体做了什么

Claude Tag 的关键不是“Slack 里有个聊天机器人”，而是它把团队协作空间变成 agent runtime 的上下文边界：

```text
Slack channel
  → scoped context
  → scoped memory
  → scoped tools / codebase / data
  → task staging
  → async execution
  → scheduled / future work
  → many Claude instances in parallel
  → admin controls
  → spend limits
  → audit log
```

Anthropic 明确说，不同 channel 的 Claude 有不同 identity 和 memory，销售 channel 的 memory 不会自动进入工程 channel；管理员可以控制每个 channel 可访问哪些工具和信息，并查看 Claude 做了什么、由谁请求。

### 3. 为什么重要

这条信号说明 agent context 正在从：

```text
individual chat session
```

转向：

```text
team workspace context
```

这带来新的系统问题：

```text
channel-level memory isolation
tool scope by workspace
ambient agent behavior
async task lifecycle
spend limit
auditability
```

尤其是“ambient / proactive agent”会增加误操作风险，所以权限和日志必须变成一等公民。

### 4. alternative approach

保守路线：

```text
DM-only bot
+ no shared memory
+ manual context paste
```

安全简单，但协作价值低。

中间路线：

```text
issue-based agent
+ explicit task queue
+ no ambient behavior
```

更可控，适合工程团队早期采用。

Claude Tag 代表的是更激进路线：

```text
workspace-native shared agent
```

价值更高，但必须有严格 scope。

### 5. 对我的启发（可执行）

如果你做内部 team agent，先不要做“全公司记忆”。应该先做：

```python
@dataclass
class ChannelScopedAgent:
    channel_id: str
    memory_namespace: str
    allowed_tools: set[str]
    allowed_repos: set[str]
    spend_limit_usd: float
    audit_log_enabled: bool = True
```

一个 channel 一个 memory namespace。跨 channel 共享必须显式授权。

## ⑤ 🆕 Google DeepMind：Gemini 3.5 Flash 内建 computer use，action safety 成为 agent runtime 必备层

**Source**：Google DeepMind — Introducing computer use in Gemini 3.5 Flash
**Time**：2026-06-24

### 1. 发生了什么

Google DeepMind 把 computer use 集成进 Gemini 3.5 Flash，让开发者构建可以在 browser、mobile、desktop 等界面中观察、推理和执行动作的 agents。官方场景包括 continuous software testing、enterprise automation、knowledge work 等 long-horizon tasks。

### 2. 工程上具体做了什么

高信号点不是“模型更强”，而是 computer-use tool 被内建到通用模型与企业 agent 平台里：

```text
Gemini 3.5 Flash
  → function calling
  → Search / Maps grounding
  → computer use
  → browser / mobile / desktop actions
  → enterprise safeguards
```

安全层也非常明确：针对 computer use 做 adversarial training；敏感或不可逆操作可以要求用户显式确认；如果检测到 indirect prompt injection，可以自动停止任务；Google 还建议结合 sandboxing、human verification、strict access controls。

### 3. 为什么重要

computer-use agent 最危险的不是“答错”，而是 真实执行错误动作：

```text
点击错误按钮
提交错误表单
删除数据
发送邮件
修改配置
泄露凭据
```

所以 agent runtime 必须有 action policy：

```text
observe
  → propose action
  → classify risk
  → require confirmation if sensitive
  → execute in sandbox / scoped environment
  → audit
```

### 4. alternative approach

可替代路线是自建：

```text
LLM planner
+ Playwright / Selenium
+ deterministic action executor
+ allowlist / denylist
+ human confirmation
```

优点是控制强、可测试；缺点是集成成本高，跨平台能力弱。Gemini 的路线是把 computer use 变成模型原生 tool，但仍然需要宿主系统提供权限边界。

### 5. 对我的启发（可执行）

你可以定义一个最小 ComputerActionPolicy：

```python
@dataclass
class ComputerAction:
    action_type: str       # click | type | submit | delete | navigate
    target: str
    reversible: bool
    external_effect: bool
    requires_confirmation: bool


def classify_action(action: ComputerAction) -> str:
    if action.external_effect and not action.reversible:
        return "high"
    if action.action_type in {"submit", "delete"}:
        return "high"
    return "low"
```

高风险动作默认不直接执行，必须进入 approval gate。

# 5️⃣ 一个工程行动（1–3 小时）

## 建一个最小 “Agent Context + Policy Gate” 控制层

目标：把本周信号落到一个可实现的小组件里。核心思想：所有 model call / tool call / memory call / computer action 都必须带 context，并先过 policy gate。

### Step 1：定义统一上下文（30 分钟）

```python
from dataclasses import dataclass
from typing import Literal

RiskLevel = Literal["low", "medium", "high"]
ActionScope = Literal["read", "write_repo", "external_api", "computer_action", "deploy"]


@dataclass(frozen=True)
class AgentContext:
    run_id: str
    actor_id: str
    org_id: str
    tenant_id: str | None
    channel_id: str | None
    budget_usd: float
    spent_usd: float
    allowed_tools: set[str]
    allowed_scopes: set[ActionScope]
```

### Step 2：定义 tool / action manifest（30 分钟）

```python
@dataclass(frozen=True)
class ToolManifest:
    name: str
    scope: ActionScope
    risk_level: RiskLevel
    reversible: bool
    requires_confirmation: bool = False
```

### Step 3：实现 policy gate（45 分钟）

```python
class PolicyViolation(Exception):
    pass


def authorize_tool_call(
    ctx: AgentContext,
    tool: ToolManifest,
    estimated_cost_usd: float = 0.0,
    confirmation_id: str | None = None,
) -> None:
    if ctx.spent_usd + estimated_cost_usd > ctx.budget_usd:
        raise PolicyViolation("budget exceeded")
    if tool.name not in ctx.allowed_tools:
        raise PolicyViolation(f"tool not allowed: {tool.name}")
    if tool.scope not in ctx.allowed_scopes:
        raise PolicyViolation(f"scope not allowed: {tool.scope}")
    if tool.risk_level == "high" and confirmation_id is None:
        raise PolicyViolation("high-risk action requires confirmation")
    if tool.scope in {"deploy", "external_api", "computer_action"}:
        if not tool.reversible and confirmation_id is None:
            raise PolicyViolation("irreversible external action requires confirmation")
```

### Step 4：每次调用都写 JSONL audit log（30–45 分钟）

```python
import json
from dataclasses import asdict
from datetime import datetime


def write_audit_log(
    ctx: AgentContext,
    tool: ToolManifest,
    status: str,
    path: str = "agent_audit_log.jsonl",
) -> None:
    event = {
        "timestamp": datetime.utcnow().isoformat(),
        "run_id": ctx.run_id,
        "actor_id": ctx.actor_id,
        "org_id": ctx.org_id,
        "tenant_id": ctx.tenant_id,
        "channel_id": ctx.channel_id,
        "tool": asdict(tool),
        "status": status,
    }
    with open(path, "a", encoding="utf-8") as f:
        f.write(json.dumps(event, ensure_ascii=False) + "\n")
```

### Step 5：写 3 个测试（30 分钟）

```text
1. high-risk computer_action 没有 confirmation → reject
2. tool 不在 allowed_tools → reject
3. estimated_cost 超过 budget → reject
```

这个小组件对应本周 5 个核心信号：

```text
AWS → tenant / identity propagation
OpenAI → evidence-backed security workflow
GitHub → model / tool / plugin governance
Anthropic → channel-scoped memory and tool access
Google → sensitive computer actions require confirmation
```

做完它，你的 agent 就不再是“模型想调用什么就调用什么”，而是开始具备生产系统需要的最小权限边界、成本控制和审计能力。
