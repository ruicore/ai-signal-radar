## ① 🆕 OpenAI：Codex 需要“持久化云工作区”，长运行 agent 进入企业基础设施阶段

**Source**：OpenAI — *OpenAI to acquire Ona*
**Time**：2026-06-11

### 1. 发生了什么

OpenAI 宣布计划收购 Ona，用于扩展 Codex 的 **secure, customer-controlled cloud infrastructure**。OpenAI 明确说，Codex 的高价值工作正在从几分钟任务变成持续数小时甚至数天的任务，因此 agent 不能继续绑定在单台本地机器或单个活跃 session 上。([[OpenAI](https://openai.com/index/openai-to-acquire-ona/)][1])

### 2. 工程上具体做了什么

核心工程方向是：

```text
Codex orchestration
+ persistent cloud workspace
+ customer-controlled execution environment
+ scoped credentials
+ activity logging
+ review workflow
```

Ona 提供的是 agent 可以长期工作的安全云环境，让 agent 在组织自己的 cloud boundary 内访问工具、系统和上下文。OpenAI 强调企业需要控制 agent 在哪里运行、能访问什么、凭据如何 scoped、活动如何记录、结果如何进入 review。([[OpenAI](https://openai.com/index/openai-to-acquire-ona/)][1])

### 3. 为什么重要

这是本周最强信号之一：**coding agent 的瓶颈正在从模型能力转向 execution substrate**。

以前的问题是：

```text
agent 能不能写代码？
```

现在的问题变成：

```text
agent 在哪里运行？
workspace 是否可恢复？
凭据如何隔离？
活动是否可审计？
长任务如何 review？
```

这说明 Codex 类系统正在向“企业级 remote execution platform”演进。

### 4. alternative approach

另一种路线是继续让 agent 跑在本地：

```text
local repo
+ local shell
+ local credentials
+ IDE session
```

优点是简单、延迟低、开发者熟悉；缺点是 laptop sleep、环境漂移、凭据暴露、缺少审计、难以并行、难以在企业规模复制。

### 5. 对我的启发（可执行）

如果你设计 coding agent，不要只设计：

```python
run_agent(prompt)
```

至少要抽象出：

```python
Workspace
Session
CredentialScope
AuditLog
ReviewGate
```

尤其是 `Workspace`，它应该是可恢复、可审计、可销毁的执行边界，而不是随手复用本地 shell。

## ② 🆕 AWS：AgentCore 把 coding agent 托管到隔离 microVM，目标是“关上 laptop 也能继续跑”

**Source**：AWS Machine Learning Blog — *It’s safe to close your laptop now: Hosting coding agents on Amazon Bedrock AgentCore*
**Time**：2026-06-08

### 1. 发生了什么

AWS 发布了一篇非常工程化的文章，讨论为什么把 coding agent 跑在 laptop 上不是生产方案，并展示如何用 Amazon Bedrock AgentCore Runtime 托管 Claude Code、Codex、Kiro、Cursor 等 coding agents。核心主张是：每个 agent session 运行在专用 Linux microVM 中，拥有持久 workspace、shell、deterministic command execution、identity、MCP gateway 和 observability。([[Amazon Web Services, Inc.](https://aws.amazon.com/blogs/machine-learning/its-safe-to-close-your-laptop-now-hosting-coding-agents-on-amazon-bedrock-agentcore/)][2])

### 2. 工程上具体做了什么

架构可以概括为：

```text
user / workflow trigger
  → AgentCore Runtime
  → isolated Firecracker microVM
  → persistent /mnt/workspace
  → deterministic shell command execution
  → AgentCore Identity / Gateway
  → CloudWatch observability
```

AWS 强调每个 session 有独立 kernel / filesystem，可以并行跑多个 agent；workspace 在 stop / resume 后保留；网络断开可以 reconnect；测试、install、push 等命令可以由 app layer deterministic 执行，而不是让模型“想办法执行”。([[Amazon Web Services, Inc.](https://aws.amazon.com/blogs/machine-learning/its-safe-to-close-your-laptop-now-hosting-coding-agents-on-amazon-bedrock-agentcore/)][2])

### 3. 为什么重要

这篇文章把 agent runtime 讲得非常像后端基础设施：

```text
isolation
persistence
deterministic execution
credential boundary
network control
observability
benchmarking
```

这正是 production agent 和 demo agent 的分界线。尤其是 deterministic command execution 很关键：不是所有动作都应该交给 LLM 决策，很多动作应该由宿主系统以确定性方式执行。

### 4. alternative approach

轻量替代方案：

```text
container-per-agent
+ Docker volume
+ Git worktree
+ Redis session state
+ OpenTelemetry
+ short-lived credentials
```

这比 microVM 轻，但隔离性、安全边界、kernel-level protection 弱一些。适合个人项目或小团队 PoC；生产环境更适合 microVM / sandbox / remote execution boundary。

### 5. 对我的启发（可执行）

设计 agent backend 时，把“模型循环”和“执行环境”分开：

```text
LLM decides intent
Runtime executes deterministic commands
Policy decides permission
Observer records trace
```

不要让模型直接拥有无限制 shell。最小实现也应该有：

```python
CommandExecutor
WorkspaceManager
CredentialBroker
TraceRecorder
```

## ③ 🆕 GitHub：Agentic Workflows 把 coding agents 编进 GitHub Actions

**Source**：GitHub Changelog — *GitHub Agentic Workflows is now in public preview* / *Agentic workflows no longer need a personal access token*
**Time**：2026-06-11

### 1. 发生了什么

GitHub 发布 Agentic Workflows public preview：开发者可以用自然语言 Markdown 定义 reasoning-based tasks，例如 issue triage、CI failure analysis、documentation updates，然后编译成标准 GitHub Actions YAML，在现有 runner / policy 体系里运行。GitHub 同周还更新：agentic workflows 不再需要 personal access token，可以使用 GitHub Actions 内置 `GITHUB_TOKEN`。([[The GitHub Blog](https://github.blog/changelog/2026-06-11-github-agentic-workflows-is-now-in-public-preview)][3])

### 2. 工程上具体做了什么

GitHub 做的是把 agent workflow 纳入 CI/CD 控制面：

```text
Markdown agent spec
  → compiled GitHub Actions YAML
  → existing runner groups
  → org policy constraints
  → sandboxed container
  → agent workflow firewall
  → threat detection job
```

安全默认值也很关键：read-only by default、integrity filter、safe outputs、threat detection job，并且通过 `GITHUB_TOKEN` 避免长期 PAT 的凭据风险。([[The GitHub Blog](https://github.blog/changelog/2026-06-11-github-agentic-workflows-is-now-in-public-preview)][3])

### 3. 为什么重要

这是 agentic coding 的一个重要形态变化：

```text
IDE assistant
  → repo-native automation
  → CI/CD-native agent workflow
```

这意味着 agent 不只是“帮人写代码”，而是会进入软件交付链路：triage、修 CI、更新文档、做 compliance report、批量 repo maintenance。

### 4. alternative approach

自建方案可以是：

```text
GitHub Actions
+ custom Python worker
+ LLM API
+ repository checkout
+ policy checks
+ PR creation
```

优点是可控；缺点是你要自己处理 token scope、sandbox、prompt injection、防泄露、workflow lockfile、cost cap、runner 策略和审计。

### 5. 对我的启发（可执行）

你的 AI coding workflow 不应该只停留在本地 Codex / Claude Code。可以选一个低风险任务做 repo-native automation：

```text
每周扫描 stale issue
分析失败 CI log
生成 changelog draft
检查 migration TODO
```

关键是先从 **read-only workflow** 开始，再逐步开放 PR write permission。

## ④ 🆕 NVIDIA：AgentPerf 让 AI 基础设施评测从“单次推理”转向“agentic workload”

**Source**：NVIDIA Technical Blog — *NVIDIA Blackwell Leads on First Agentic AI Infrastructure Benchmark*
**Time**：2026-06-12

### 1. 发生了什么

NVIDIA 发布 AgentPerf benchmark 相关结果，强调传统 inference benchmark 主要测单次模型调用，无法代表 agentic AI。AgentPerf 基于真实 coding agent trajectories：任务需要读写代码、编辑文件、执行命令、迭代，并模拟代表性的 CPU-side tool time，用来衡量并发任务、响应时间、成本和能耗。([[NVIDIA Blog](https://blogs.nvidia.com/blog/nvidia-blackwell-agentperf-artificial-analysis/)][4])

### 2. 工程上具体做了什么

AgentPerf 的核心不是单模型跑分，而是 workload-level benchmark：

```text
coding task trajectory
  → multiple LLM calls
  → tool calls
  → command execution
  → iteration
  → concurrency threshold
  → useful work per dollar / watt
```

NVIDIA 也强调 Blackwell / TensorRT-LLM 等系统优化，例如将 input processing 和 output generation 分离，以提升 agentic workload 下的吞吐。([[NVIDIA Blog](https://blogs.nvidia.com/blog/nvidia-blackwell-agentperf-artificial-analysis/)][4])

### 3. 为什么重要

这说明 AI infra 评估指标正在变化：

```text
tokens/sec
  → tasks completed per dollar
  → agents per megawatt
  → latency under concurrent agent workflows
```

对于 long-running agents，单次推理延迟不够解释真实成本。真正要看的是完整任务完成成本、并发能力、tool latency、失败重试、validation loop。

### 4. alternative approach

传统评测方式：

```text
single prompt
single model response
tokens/sec
price per 1M tokens
```

问题是它忽略了 agent 的真实结构：planning、tool call、context growth、retry、test execution、repair loop。更实用的替代是自己维护一组 task-level benchmark。

### 5. 对我的启发（可执行）

你的 agent 评测不要只记录 token。至少记录：

```text
task_success
wall_time
total_cost
num_llm_calls
num_tool_calls
retry_count
human_intervention_count
```

最终优化目标应该是：

```text
cost per successful task
```

而不是单次调用便宜。

## ⑤ 🆕 Anthropic：Claude Managed Agents 增加 schedule 与 vault，connector 也开始有观测面

**Source**：Anthropic — *New in Claude Managed Agents: run agents on a schedule and store environment variables in vaults* / *Connector Observability and In-App Directory Submission*
**Time**：2026-06-09 / 2026-06-08

### 1. 发生了什么

Anthropic 给 Claude Managed Agents 增加两个关键能力：scheduled agents 和 vaults。scheduled agents 可以按 cron-like schedule 启动新 session 执行任务；vaults 用于保存环境变量，让 agent 访问 CLI tools、API、authenticated services、MCP servers。Anthropic 同周还为 connectors 提供 observability dashboard，包括 active users、tool calls、health score、error rates、latency、per-tool breakdown 和 usage by product。([[Claude](https://claude.com/blog/whats-new-in-claude-managed-agents)][5])

### 2. 工程上具体做了什么

可以理解为 Anthropic 在补两个 production primitive：

```text
Scheduled execution
  → recurring agent task
  → pause / resume / archive / manual trigger

Secret boundary
  → env vars in vault
  → keys attached at network boundary
  → model does not receive raw key

Connector observability
  → tool call metrics
  → error rate
  → latency
  → health score
```

尤其是 vault 的设计重点是：凭据不直接交给模型，而是在允许的网络边界上附加真实 key。([[Claude](https://claude.com/blog/whats-new-in-claude-managed-agents)][5])

### 3. 为什么重要

这说明 hosted agents 正在从“交互式工具”变成“可运营服务”：

```text
schedule
secrets
external systems
MCP tools
connector health
latency / error metrics
```

一旦 agent 可以定时跑、访问外部服务、调用 MCP，它就必须被当作 backend worker 管理，而不是 chat session。

### 4. alternative approach

自建轻量方案：

```text
cron / Celery beat / GitHub Actions schedule
+ Vault / AWS Secrets Manager
+ MCP server allowlist
+ OpenTelemetry metrics
+ retry / dead-letter queue
```

优点是更可控；缺点是你要自己处理 agent identity、secret injection、tool observability、schedule state、失败重试和权限边界。

### 5. 对我的启发（可执行）

如果你做定时 agent，不要直接把 API key 放进 prompt 或环境里乱传。至少设计：

```python
AgentIdentity
SecretScope
AllowedDomains
ToolCallMetrics
ScheduleState
```

一个可上线的 scheduled agent，本质是一个带 AI 决策层的定时 worker。

# 5️⃣ 一个工程行动（1–3 小时）

## 给你的 coding agent / LLM backend 设计一个“Remote Workspace Contract”

目标：不用马上搭完整 microVM 平台，但先把 agent execution substrate 的接口设计出来。这个行动直接对应本周 OpenAI Ona、AWS AgentCore、GitHub Agentic Workflows 的共同信号。

### Step 1：定义 workspace 生命周期（30 分钟）

```python
from dataclasses import dataclass
from datetime import datetime
from enum import StrEnum


class WorkspaceStatus(StrEnum):
    CREATING = "creating"
    RUNNING = "running"
    PAUSED = "paused"
    STOPPED = "stopped"
    DESTROYED = "destroyed"


@dataclass
class AgentWorkspace:
    workspace_id: str
    repo_url: str
    branch: str
    base_commit: str
    status: WorkspaceStatus
    created_at: datetime
    last_active_at: datetime
    retention_hours: int = 24
```

### Step 2：定义命令执行边界（30–45 分钟）

```python
@dataclass
class CommandRequest:
    workspace_id: str
    command: list[str]
    cwd: str
    timeout_sec: int
    requested_by: str
    reason: str


@dataclass
class CommandResult:
    exit_code: int
    stdout_tail: str
    stderr_tail: str
    duration_ms: int
```

关键约束：

```text
LLM 只能提出 CommandRequest
Runtime 决定是否执行
Runtime 记录 CommandResult
```

不要让模型直接拥有裸 shell。

### Step 3：定义凭据 scope（30 分钟）

```python
@dataclass
class CredentialScope:
    workspace_id: str
    allowed_domains: list[str]
    allowed_tools: list[str]
    expires_at: datetime
    read_only: bool = True
```

最小规则：

```text
default read-only
short-lived token
domain allowlist
tool allowlist
never expose raw secrets to model text
```

### Step 4：定义审计日志（30–45 分钟）

```python
@dataclass
class WorkspaceAuditEvent:
    workspace_id: str
    event_type: str   # command_requested | command_executed | file_changed | pr_created
    actor: str        # user | agent | runtime
    summary: str
    created_at: datetime
```

目录结构可以先这样：

```text
agent_runtime/
  workspace.py
  command_executor.py
  credential_scope.py
  audit_log.py
  tests/
```

### Step 5：写 3 个测试（30 分钟）

```text
1. read-only workspace 不允许 push
2. command timeout 后必须返回失败状态
3. expired credential scope 不允许 tool call
```

这个小动作的意义：你会从“LLM 应用开发”切到“agent execution platform 设计”。本周所有高信号都在指向同一个结论：

```text
未来 AI coding 的核心竞争力，不只是 prompt，而是安全、持久、可观测、可恢复的执行系统。
```
