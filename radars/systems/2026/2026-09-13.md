**观察窗口：2026 年 9 月 7 日—9 月 13 日**

本次执行仅基于当前 7 天窗口重新检索和验证公开来源，不使用此前报告作为事实输入。本期保留 **5 个高信号变化**：Inference Routing、Agent Evaluation、GPU Systems Programming、Massive Multi-agent Orchestration，以及生产 SRE Agent。

本周最值得保留的总体判断是：

> **AI Systems 正在从“模型性能优化”进入“计算状态、Agent 行为和现实权限都成为调度对象”的阶段。**
> Router 开始理解 KV Cache；CI 开始理解 Agent Trajectory；编程语言安全边界延伸到 GPU Kernel；数千 Agent 被当成分布式搜索计算；生产 Agent 则被明确区分为信息权限、执行权限和跨系统协调权限。

# 1. Executive Summary

* **Inference Routing 正在从 Load Balancing 变成 Data-locality Scheduling。** AWS 9 月 10 日为 SageMaker Inference 引入 Prefix-aware Routing：Router 根据请求前缀把重复上下文送往已经持有相关 KV Cache 的实例。AWS 在 Llama 3.1 70B 的测试中报告 P50 TTFT 最多下降 77%、KV Cache Hit 从约 25% 提高到 80% 以上；更重要的是，独立开源实验同时证明纯 Affinity 在 Hot Prefix 下可能因为负载倾斜反而降低 Goodput。长期方向不是“永远按 Prefix 路由”，而是 **Cache Locality × Queue Load × Tenant Isolation 的联合调度**。([Amazon Web Services, Inc.][1])

* **Agent Evaluation 正式进入 CI/CD Quality Gate。** AWS 本周给出一套可运行 Reference Pipeline：Agent 部署到 AgentCore Runtime，使用带角色权限的 MCP Tool，通过 OTel Trace 评估 Helpfulness、Correctness、Tool Selection、Tool Parameter 和完整 Tool Trajectory；分数退化时 GitHub PR 直接失败。Agent 行为开始像 Test Suite 一样成为 Build Artifact，而不是上线后才观察的主观属性。([Amazon Web Services, Inc.][2])

* **Rust 正跨过 CPU Runtime 边界进入 GPU Kernel。** NVIDIA 9 月 8 日公开 CUDA Rust 双路径：`cuda-oxide` 面向 SIMT、直接把 Rust 编译到 PTX；`cutile-rs` 面向 Tile Programming，并在 Stable Rust 上通过 CUDA Tile IR JIT 编译。CUDA C++ 不会因此消失，但 AI Infra 已经出现一个长期趋势：**Inference Engine、Runtime、Driver 和 Kernel 逐渐可以共享更一致的类型与内存安全体系**。([NVIDIA Developer][3])

* **Multi-agent Architecture 已经能够扩展到“计算集群”级规模，但协调而非 Agent 数量成为核心问题。** OpenAI 9 月 8 日披露其 Navier–Stokes 研究运行：产生解法的工作组涉及约 10,000 个并发 Agent，不同群组探索不同问题变体，运行期间动态重新分配 Agent、升级 Model，并使用 Codex 汇总各组 Intermediate Result，最后用 Lean 做形式验证。无论最终数学结论的外部学术审查如何，其系统架构已经展示一种重要模式：**Agent Swarm 更接近 Distributed Search + Artifact Synthesis + Deterministic Verification，而不是“大量 Chatbot 同时工作”。** ([OpenAI][4])

* **生产 Agent 的可靠形态越来越不像一个全能 Agent，而像围绕 Durable Operational Object 的多个受限角色。** Microsoft 本周公开其内部网络运维实践：Troubleshooting、跨团队 Handoff 和 Outage Communication 分别由不同 Agent 处理；信息查询面向较广人群，设备级执行只开放给特定工程师和安全管理工作站，跨团队 Ticket 仍保留人工批准。长期可复用的并不是这些具体 Agent，而是 **Specialization + Capability Separation + Fresh State + Outcome Validation**。([Microsoft][5])

# 2. Top 5 AI Systems Signals

## Signal 1：KV Cache 正进入 Router 的决策状态

**Source:** AWS — *Reduce LLM latency with prefix-aware routing on Amazon SageMaker Inference*
**Date:** 2026-09-10
**Evidence Level:** **Official**
**Technology Maturity:** **Production Adoption**

### 1. 发生了什么

Prefix Caching 本身并不新。vLLM、TensorRT-LLM 等 Runtime 已经可以保留重复 Prompt Prefix 的 KV Cache。

问题发生在多 Replica 场景：

```text
request 1 → GPU A → cache prefix X
request 2 → GPU B → recompute X
request 3 → GPU C → recompute X
```

传统 Round-robin 或 Least-load Router 并不知道哪个 Worker 已经计算过哪些 Prefix，因此 Fleet 扩容以后，单机 Prefix Cache 的价值会被路由层稀释。

SageMaker Prefix-aware Routing 将同一前缀稳定地映射到同一实例，同时保留 Overload Protection。AWS 在 7 台 `ml.p5.48xlarge`、Llama 3.1 70B、vLLM Prefix Caching 的测试中报告：8K Shared Prefix 场景下 P50 TTFT 减少约 71–77%，P90 减少约 33–37%，KV Hit 从约 25% 上升到约 82%，Throughput 提升约 15–16%；Router 本身增加约 1.3–1.9 ms 开销。上述数字均为 AWS 自有 Benchmark。([Amazon Web Services, Inc.][1])

### 2. 工程上改变了什么

普通负载均衡：

```text
target =
    f(
        health,
        outstanding_requests
    )
```

LLM-aware Routing 越来越接近：

```text
target =
    f(
        queue_load,
        cached_prefix,
        prefix_length,
        session_affinity,
        KV_capacity,
        tenant,
        topology
    )
```

也就是说：

> **已计算状态的位置，本身成为 Scheduling Input。**

这与传统 Data-local Scheduling、NUMA-aware Scheduling、Hadoop Data Locality 实际上属于同一类系统问题。

### 3. Architecture impact

未来 LLM Serving Control Plane 很可能显式维护：

```text
Request
  │
  ├── Prefix Hash
  ├── Tenant
  ├── Session
  └── SLA
        │
        ▼
    KV-aware Router
  ┌─────┼────────┐
  ▼     ▼        ▼
GPU A  GPU B    GPU C
 X,Y     Z       X,Q
```

但这里存在一个非常重要的矛盾：

> **Cache Locality 与 Load Locality 并不总是同方向。**

一个 Hot Prefix 全部落到 GPU A 时，即使每次都 Cache Hit，Queueing Cost 也可能超过重新 Prefill 的成本。

这并非理论问题。一个近期公开、带 H200 Benchmark Artifact 的独立 Serving Project 明确报告：其 Prefix-affinity Router 没有击败 Load-aware Baseline；在 `hot_prefix_skew` 的高负载实验中 Goodput 反而低约 23%。另一个 llm-d Benchmark 也显示，在共享长文档场景中，Load-aware Placement + P2P KV Pull 的 Warm Throughput 比纯 Prefix Affinity 高约 35%。([GitHub][6])

所以长期架构更可能是：

```text
local KV hit
        vs
queueing cost
        vs
remote KV transfer
        vs
recompute
```

的动态选择。

### 4. Alternative approach 和 trade-off

| 策略                     | 优点                  | 主要代价                  |
| ---------------------- | ------------------- | --------------------- |
| Round-robin            | 极简单、无状态             | Cache Locality 很差     |
| Least outstanding      | 负载均衡好               | 可能不断丢失 Prefix Cache   |
| Session stickiness     | Multi-turn 简单       | 容易形成热点                |
| Prefix affinity        | Prefill Reuse 高     | Hot Prefix 会导致负载倾斜    |
| Hybrid affinity + load | 平衡 Locality 与 Queue | Router 状态复杂           |
| Load-aware + P2P KV    | Compute / Data 可分离  | 网络传输和 KV Metadata 更复杂 |

### 5. 对 AI Systems Engineer 的启发

以后做 Inference Router，不应该只问：

> 哪台 GPU 最空？

也不能只问：

> 哪台 GPU 有 Cache？

更合理的问题是：

> **去已有 Cache 的 Worker 等队列，和去空闲 Worker 重新计算 Prefix，哪个更便宜？**

因此 Router 的决策最好可观测：

```text
request_id
prefix_hash
prefix_tokens
candidate_workers
cache_hit_estimate
queue_depth
selected_worker
routing_reason
estimated_saved_prefill
tenant_namespace
```

否则 TTFT 退化时，你只能看到“模型变慢”，却不知道真正失败的是 Placement Policy。

## Signal 2：Agent Evaluation 开始成为 Pull Request 的正式 Quality Gate

**Source:** AWS — *Automated agent evaluation with Amazon Bedrock AgentCore and GitHub Actions*
**Date:** 2026-09-08
**Evidence Level:** **Reproducible Engineering Practice**
**Technology Maturity:** **Production Adoption**

### 1. 发生了什么

AWS 本周发布一套完整 Reference Implementation：

```text
GitHub PR
   ↓
deploy test agent
   ↓
AgentCore Runtime
   ↓
OAuth-protected MCP
   ↓
generate OTel trace
   ↓
AgentCore Evaluation
   ↓
threshold
   ↓
PASS / BLOCK PR
```

AgentCore Evaluation 可以针对：

* Helpfulness；
* Correctness；
* Goal Success；
* Tool Selection Accuracy；
* Tool Parameter Accuracy；

做评分，还支持三个 Tool Trajectory Evaluator：

* Exact Order Match；
* In-order Match；
* Any-order Match。

除了 LLM-as-a-judge，还可以通过 Lambda 使用 Code-based Evaluator。评估又分 On-demand、Online 与 Batch 三种模式。([Amazon Web Services, Inc.][2])

### 2. 工程上改变了什么

传统 Agent 开发经常是：

```text
change prompt
→ manual chat
→ looks good
→ deploy
```

生产化以后更合理的单位是：

```text
Agent Version
=
code
+ model
+ prompt
+ tool schema
+ permissions
```

任何其中一项变化：

```text
system_prompt changed
model changed
MCP tool changed
RBAC changed
tool description changed
```

都应该触发相同的 Regression Suite。

Agent 行为由此第一次真正进入：

> **Software Delivery Lifecycle。**

### 3. Architecture impact

一个成熟 Agent Delivery Pipeline 可以分成：

```text
Build Plane
   │
   ▼
Agent Artifact
   │
   ▼
Ephemeral Evaluation Environment
   │
   ├── representative tasks
   ├── multiple roles
   ├── MCP tool access
   └── failure injection
   │
   ▼
Trace
   │
   ├── response eval
   ├── trajectory eval
   ├── deterministic assertion
   └── security assertion
   │
   ▼
Promotion Gate
```

特别值得注意的是，该 Reference Pipeline 同时处理：

* GitHub Actions 到 AWS 的 OIDC；
* CI 的 Machine-to-machine OAuth；
* MCP Server 中的角色权限；
* 用户态与 CI 身份的差异。

这说明 Agent Eval 不能只验证“回答质量”，还必须验证：

> **在什么身份下，它实际能够调用什么。** ([Amazon Web Services, Inc.][2])

### 4. Alternative approach 和 trade-off

| Eval 方法                | 优点        | 局限                            |
| ---------------------- | --------- | ----------------------------- |
| Manual test            | 快速探索      | 不可复现                          |
| LLM Judge              | 扩展性高      | Judge Bias / Correlated Error |
| Code assertion         | 确定性强      | 只能覆盖可形式化行为                    |
| Expected trajectory    | Tool 行为明确 | 可能过度限制合理新路径                   |
| Outcome-based eval     | 最接近价值     | Often slow / expensive        |
| Production online eval | 真实分布      | 已经有用户风险                       |

真正合理的系统通常是：

```text
LLM Judge
+
Deterministic Check
+
Trajectory Check
+
Production Outcome
```

而不是只设置：

```text
judge_score >= 0.8
```

### 5. 对 AI Systems Engineer 的启发

Agent CI 建议至少区分四层：

| Layer      | 示例             |
| ---------- | -------------- |
| Response   | 答案是否正确         |
| Tool       | 是否选对 Tool / 参数 |
| Trajectory | 是否以允许的方式完成     |
| Outcome    | 外部状态是否真的正确     |

尤其不要把：

```text
正确答案
```

误认为：

```text
正确执行
```

一个 Agent 可能给出正确结论，却访问了本不应访问的数据，或者执行了多余的写操作。

## Signal 3：Rust 正进入 CUDA Kernel 层

**Source:** NVIDIA — *Introducing CUDA Rust: Two Tracks for Writing GPU Kernels*
**Date:** 2026-09-08
**Evidence Level:** **Official**
**Technology Maturity:** **Open Source Experiment**

### 1. 发生了什么

NVIDIA 本周公开两条 CUDA Rust 路径。

**`cuda-oxide`**

```text
Rust SIMT Kernel
→ custom rustc backend
→ Pliron IR
→ LLVM
→ PTX
```

面向熟悉 CUDA Thread / Block 模型的开发者，目前属于 Early Alpha，并依赖 Pinned Nightly Rust 与 LLVM。

**`cutile-rs`**

```text
Stable Rust
→ tile abstraction
→ CUDA Tile IR
→ JIT
```

开发者描述 Tensor / Tile 运算，而 Compiler 管理 Thread Mapping 和 Memory Layout。它运行在 Stable Rust 1.89+、CUDA 13.3，并已经被 Hugging Face Grout Inference Engine 和 `mistral.rs` 使用。([NVIDIA Developer][3])

### 2. 工程上改变了什么

AI Systems 的 Host Side 已经越来越 Rust-heavy：

```text
Gateway
Scheduler
Inference runtime
Driver
Agent runtime
```

但 GPU Kernel 长期仍主要是：

```text
CUDA C++
```

这产生大量：

```text
Rust
↔ FFI
↔ C++
↔ CUDA
```

边界。

CUDA Rust 如果成熟，可以形成：

```text
Rust service
→ Rust runtime
→ Rust scheduling
→ Rust kernel
```

并把一部分：

* Lifetime；
* Ownership；
* Aliasing；
* Memory Access；

错误提前到 Compile Time。

### 3. Architecture impact

这里最重要的不是语言偏好，而是 **Safety Boundary 往 GPU 下沉**。

`cuda-oxide` 使用类似 `DisjointSlice` 与 Launch Contract 的机制避免非法 Alias；`cutile-rs` 则通过 Tensor Partition / Ownership 保证 Exclusive Access。([NVIDIA Developer][3])

未来高性能 AI Runtime 可能更自然地拆成：

```text
Safe orchestration
      │
      ▼
Typed GPU abstraction
      │
      ▼
Unsafe / hardware-specific core
```

而不是大面积依赖手工 Pointer Discipline。

### 4. Alternative approach 和 trade-off

| 方法          | 优点                           | 局限                            |
| ----------- | ---------------------------- | ----------------------------- |
| CUDA C++    | 最成熟、生态最大                     | 内存安全依赖开发者                     |
| Triton      | Kernel 编写简单                  | 控制能力和覆盖面有限                    |
| CUDA Python | 开发体验好                        | Systems integration 不同        |
| cutile-rs   | Stable Rust、Tile portability | 新生态、抽象可能限制极致控制                |
| cuda-oxide  | SIMT 控制细                     | Nightly Toolchain、Early Alpha |

需要特别避免一个误解：

> Rust ≠ GPU Kernel 自动安全。

FFI、`unsafe`、Driver Bug、Race、Numerical Error、Kernel Logic Error 仍然存在。

它主要消除的是一部分**可静态表达的内存错误类别**。

### 5. 对 AI Systems Engineer 的启发

值得关注的不是“是否把所有 CUDA 重写成 Rust”，而是：

> **Inference Engine 是否可以拥有从 Control Plane 到 Kernel 更统一的类型和安全模型。**

特别值得持续跟踪：

* Tensor ownership；
* Async GPU lifetime；
* CUDA Graph；
* NCCL / networking interop；
* Profiling tool support；
* C++ / Python interoperability；
* Kernel performance parity。

NVIDIA 已明确计划继续推进 CUDA Rust 与 CUDA C++ / Python 的互操作，而不是构建封闭的新生态。([NVIDIA Developer][3])

## Signal 4：Multi-agent 开始表现为大规模 Distributed Search System

**Source:** OpenAI — *On the Navier–Stokes Millennium Prize Problem*
**Date:** 2026-09-08
**Evidence Level:** **Official**
**Technology Maturity:** **Demo**

### 1. 发生了什么

OpenAI 报告其系统生成了 Navier–Stokes 问题的一套分析证明与 Lean Formalization。这里不对数学结论是否最终得到独立学术共同体接受作额外判断；本报告关注的是其公开的执行架构。

产生最终结果的 Agent Group 涉及约 **10,000 个并发 Agent**。系统进行了几项很值得注意的工程操作：

* 不同 Agent Group 接收不同 Problem Variant；
* Group 内可以交流；
* Agent 可以访问缓存互联网和代码执行；
* 约 100 个 Agent 曾持续约 50 小时探索 Euler 相关问题；
* 当某一方向显示更高希望时，系统把其他问题的 Agent 重新调度过去；
* 运行期间更强的 Model Checkpoint 可用后，Agent 被切换到新版本；
* Codex 被用于汇总不同组的 Intermediate Insight，再反馈给后续搜索。([OpenAI][4])

### 2. 工程上改变了什么

这已经不能用：

```text
manager agent
→ sub agents
```

简单理解。

更接近：

```text
                 Search Controller
                        │
        ┌───────────────┼───────────────┐
        ▼               ▼               ▼
 Search island A   Search island B   Search island C
    1000 agents       4000 agents       ...
        │               │
        └──────┬────────┘
               ▼
        Artifact Reducer
               │
      cross-pollination
               │
               ▼
       new search frontier
               │
               ▼
        Formal verifier
```

这是典型的：

* Work Scheduling；
* Search Diversity；
* Resource Reallocation；
* Intermediate Artifact Storage；
* Reducer；
* Verification；

问题。

### 3. Architecture impact

当 Agent 数达到数千时，主要架构问题不再是 Prompt，而是：

```text
Which agents explore what?
When do we stop a branch?
When do we duplicate a promising branch?
What intermediate results are reusable?
How is provenance preserved?
How do we prevent groupthink?
Who synthesizes 10,000 outputs?
```

一个真正的大规模 Multi-agent Platform 很可能需要：

```text
Task DAG
Artifact Store
Search Budget
Priority Queue
Agent Lease
Checkpoint
Reducer
Verifier
Lineage Graph
```

而不是单纯 Message Bus。

### 4. Alternative approach 和 trade-off

| 方法                   | 优点                | 风险                                  |
| -------------------- | ----------------- | ----------------------------------- |
| Single long agent    | Context 连贯        | Search breadth 小                    |
| N independent agents | Diversity 高       | 重复工作严重                              |
| Hierarchical agents  | 容易管理              | Coordinator Bottleneck              |
| Island / group model | 兼顾多样性与交流          | Cross-group synthesis 复杂            |
| Massive swarm        | Search breadth 极大 | Token / Compute / Coordination 成本巨大 |

Agent 数量本身也绝不是质量指标。

OpenAI 报告整个相关探索产生数百万消息和数百亿级 Output Token，这说明：

> **Scaling Search 需要巨大的 Compute Budget，并不等于简单横向增加 Agent 会普遍划算。** ([OpenAI][4])

### 5. 对 AI Systems Engineer 的启发

大规模 Agent Orchestration 应优先设计：

```text
budget
ownership
artifact provenance
search diversity
branch termination
resource reallocation
checkpoint
reducer quality
verification
```

而不是先设计更多 Agent Persona。

尤其是 Reducer / Synthesizer 可能成为真正的新瓶颈：

> 搜索能力扩大 100 倍之后，如果只能用一个 Model 顺序读完所有结果，系统整体并没有真正扩展。

## Signal 5：生产 SRE Agent 的核心是 Capability Separation 与 Incident Lifecycle

**Source:** Microsoft Digital — *From alerts to action: How AI agents are reshaping network operations at Microsoft*
**Date:** 2026-09-10
**Evidence Level:** **Official**
**Technology Maturity:** **Production Adoption**

### 1. 发生了什么

Microsoft 内部网络覆盖超过 900 个站点、500 个数据中心、75,000+ 设备和 100 万以上 Connected Endpoint。Microsoft Digital 将 Agent 优先放在三个高成本节点：

1. Dynamic Troubleshooting；
2. Cross-system Handoff；
3. Outage Communication。([Microsoft][5])

对应地，没有设计一个“Network Super Agent”，而是几个不同角色：

**Falcon Agent**

* 刷新故障诊断；
* 获取最新 Log；
* 检查 Device Reachability；
* 验证服务恢复；
* 更新 Incident。

但 Executional Prompt 仅允许特定工程师在 Secure Admin Workstation 使用；Information Query 可以提供给更多人。([Microsoft][5])

**Smart Bonding Agent**

* 推荐需要联系的团队；
* Human Approval 后创建 Ticket；
* 监控外部团队更新；
* 调度 Work Window。

**Outage Insights Agent**

* 向相关人群主动推送；
* 回答 Incident Status、Impact、ETA 和历史趋势。([Microsoft][5])

### 2. 工程上改变了什么

传统 Incident Automation 经常围绕：

```text
runbook
```

设计。

Agent 使流程更适合：

```text
incident object
```

设计。

一个 Incident 拥有：

```text
state
telemetry
diagnostics
owners
handoffs
approvals
actions
communications
resolution evidence
```

多个 Agent 围绕同一个 Durable Object 工作，而不是各自维护一份隐式 Chat Context。

### 3. Architecture impact

一个更稳健的 Operational Agent Architecture 可能是：

```text
                  Incident State
                        │
       ┌────────────────┼─────────────────┐
       ▼                ▼                 ▼
 Diagnosis Agent   Handoff Agent    Comms Agent
       │                │                 │
 read + limited     ticket write       read-only
 execution          with approval
       │                │
       └──────────┬─────┘
                  ▼
           Resolution Evidence
```

这里最值得学习的是权限并不跟：

```text
Agent identity
```

简单绑定。

而是跟：

```text
user
device
operation
incident state
```

联合绑定。

### 4. Alternative approach 和 trade-off

**一个通用 Operational Agent**

优点：

* 用户体验简单；
* Context 看起来完整。

缺点：

* Permission Surface 巨大；
* Prompt Injection Blast Radius 大；
* 很难定位错误责任。

**多个 Specialist Agent**

优点：

* Capability Boundary 明确；
* 独立 Eval；
* 独立权限；
* 失败范围较小。

缺点：

* Handoff；
* Shared State；
* Coordinator；
* Duplicate Work。

Microsoft 当前更接近后者。

### 5. 对 AI Systems Engineer 的启发

生产 Agent 的权限设计应该区分：

```text
Read
Suggest
Create external work
Execute
Validate
Communicate
```

不要只有：

```text
agent_can_use_tool = true
```

Microsoft 自报 Falcon 前几个月累计节省约 300 小时、每 Ticket 约 10–15 分钟，并称其可覆盖约 60% Incident Volume；这些属于公司内部指标，并非独立验证。但其架构模式本身比这些效率数字更值得保留。([Microsoft][5])

本周我最建议精读它，因为它把三个非常重要的分布式系统概念连接到了一起：

```text
Data Locality
+

```

Prefix Caching 单机很容易理解。

真正困难的是：

> **进入 Cluster 后，你究竟应该把 Work 送到空闲 Compute，还是送到已有 State？**

这与：

* Database Cache Routing；
* CDN；
* Hadoop Data Locality；
* Stateful Service Placement；
* NUMA；

都有相似之处。

所以它非常适合训练 Systems Judgment，而不只是学习一个 AWS Feature。

## Reading Guide

### 1. 先读问题定义

重点：

* 为什么 Single-instance Prefix Caching 有效；

> Cache 存在哪里？

以及：

> Router 知不知道 Cache 存在哪里？

这两个问题完全不同。

特别比较：

* 8K Shared Prefix；

* P50 vs P90；
* Throughput；
* KV Cache Hit；
* Routing Overhead。

AWS Benchmark 表明 Long Shared Prefix 获益明显高于 Short Context。([Amazon Web Services, Inc.][1])

```text
routing value
≈
prefix reuse value
-
load skew cost
-
routing overhead
```

### 3. 读两个关键参数

SageMaker 暴露：

```text
PrefixLength

```

前者决定 Router 用请求的多少前缀参与 Affinity 判断；后者限制目标实例过载时是否继续坚持 Affinity。([Amazon Web Services, Inc.][1])

这两个参数实际上分别对应：

```text
Locality Strength
vs
Load Protection
```

---

### 4. 认真读 Tenant Isolation

SageMaker 支持通过显式 Prefix-aware ID / Prompt Cache Key 将 Routing Identity 与原始 Prompt 解耦。

这非常重要。

不能简单认为：

```text
same text
=
same security domain
```

两个 Tenant 即使 System Prompt 完全相同，也未必应该共享同一 Cache Namespace。([Amazon Web Services, Inc.][1])

### 5. 推荐代码目录

SageMaker Router 本身属于托管服务，核心实现没有公开源码；因此不要浪费时间寻找其内部 Router Code。

前者负责 Prefix Cache Hit、Block Allocation、Eviction 和统计；后者包含 Block Hash、Cache Salt、跨进程可重复 Prefix Hash 等逻辑。([GitHub][7])

尤其值得注意：

```text
cache_salt
```

本身就是 Cache Isolation Primitive。

## Practical Experiment：构建一个最小 KV-aware Router Simulator

**时间：约 2 小时，不需要 GPU。**

### 目标

不要证明：

> Prefix-aware Routing 最好。

而是验证：

> **什么情况下 Locality 胜过 Load，什么情况下相反。**

### Step 1：定义三个 Worker

```text
A:
queue = 0
cache = {X}

B:
queue = 0
cache = {Y}

C:
queue = 0
cache = {}
```

Prefix：

```text
X = 8,000 tokens
Y = 2,000 tokens
Z = unique
```

---

### Step 2：实现四种 Router

```text
round_robin()

least_loaded()

prefix_affinity()

hybrid()
```

Hybrid 可以很简单：

```text
if cache_hit_worker.queue_cost
   < recompute_cost_on_least_loaded:
       route cache worker
else:
       route least loaded
```

---

### Step 3：建立简化成本模型

例如：

```text
TTFT =
queue_wait
+
uncached_tokens / prefill_rate
+
routing_overhead
```

不追求模拟真实 GPU，只要保持四种策略使用相同模型即可。

---

### Step 4：运行四类流量

#### A. No sharing

```text
100% unique prefix
```

预期：

> Prefix Routing 没价值。

#### B. Stable shared prefix

```text
80% X
20% unique
```

低流量时 Affinity 应明显获益。

#### C. Hot prefix overload

```text
95% X
arrival_rate > worker A capacity
```

观察 Pure Affinity 何时输给 Load-aware。

#### D. Multiple reusable prefixes

```text
40% X
40% Y
20% unique
```

观察 Worker Placement 是否趋向稳定。

---

### Step 5：记录

| Metric            | 含义              |
| ----------------- | --------------- |
| Cache hit rate    | Prefix reuse    |
| Recomputed tokens | 浪费的 Prefill     |
| Queue variance    | Fleet imbalance |
| P50 TTFT          | 常规体验            |
| P95 TTFT          | Tail latency    |
| Throughput        | Fleet capacity  |

最后画：

```text
x = offered load
y = TTFT
```

分别比较四条 Routing Strategy。

---

## 验证方式

实验最终应该出现一个“相图”而不是单一 Winner：

```text
Low reuse
→ load-aware

High reuse + low load
→ prefix affinity

High reuse + hot prefix
→ hybrid

Extreme load + shared remote KV
→ consider load-aware + KV transfer
```

如果得到了这种结果，就真正理解了本周这条信号。

# 4. Research Direction

## 4.1 Router 正成为 AI Serving 的真正 Scheduler

Prefix-aware Routing、KV Sharing、Session Affinity、LoRA Placement、P/D Disaggregation 都在把 Router 推向：

```text
HTTP Load Balancer
        ↓
Inference Scheduler
```

未来它可能同时理解：

```text
queue
KV locality
adapter locality
session locality
GPU topology
SLA
cost
```

本周 AWS 的 Production Feature 与独立负结果共同说明：

> **Routing 将是多目标优化，而不是某一种 Affinity Algorithm。** ([Amazon Web Services, Inc.][1])

---

## 4.2 Agent Eval 会变成标准 CI Primitive

AWS 已经把：

```text
prompt/model/tool change
→ deploy
→ trace
→ eval
→ block merge
```

做成完整 Reference Pipeline。([Amazon Web Services, Inc.][2])

GitHub 本周的另一个方向也值得一起看：企业可以集中管理 Copilot Sandbox 的 Filesystem、Network、Proxy、Developer Tool 和 macOS Keychain 权限，并提供 Policy Diagnostics。([The GitHub Blog][8])

两者结合起来，会逐渐形成：

```text
Agent CI =
behavior regression
+
permission regression
+
security regression
```

而不仅是 Answer Quality。

---

## 4.3 GPU Systems Layer 会逐渐采用更强类型和内存安全语言

CUDA Rust 目前还很早，尤其 `cuda-oxide` 仍是 Alpha。

但 NVIDIA 已经明确指出其：

* Linux Driver；
* Dynamo Core；
* NVTX bindings；

等 AI Systems Component 正使用 Rust。([NVIDIA Developer][3])

如果 Kernel 层也成熟，未来一部分 AI Infrastructure Stack 会出现真正的：

```text
Rust top to bottom
```

路径。

这并不会消灭 CUDA C++，但值得长期关注 **Safety without Python-level abstraction cost** 这一方向。

---

## 4.4 Multi-agent 会越来越像 HPC / Search Infrastructure

10,000 Agent 并不意味着以后每个任务都需要 10,000 Agent。

真正的长期信号是：

```text
search workers
+
shared artifacts
+
resource scheduler
+
reducers
+
verification
```

开始成为 Agent Architecture 的自然抽象。([OpenAI][4])

因此未来的 Multi-agent Platform 很可能借鉴：

* Distributed Search；
* Ray / Actor Systems；
* HPC Scheduling；
* MapReduce；
* Beam Search；
* Evolutionary Search；

而不是只借鉴组织结构里的“Manager / Worker”。

---

## 4.5 Agent Security 要假设“长时间、持久状态、无人值守”已经存在

Anthropic 9 月 10 日的 Threat Intelligence 报告显示，真实恶意活动已经出现：

* Lead Agent + Sub-agent Swarm；
* Persistent Campaign Memory；
* 跨 Working Session 保存 Target、Credential 和 Engagement State；
* Scheduled Agent Fleet；
* 无人在场时持续收集；
* 自动续签被窃取 Token。([Anthropic][9])

这意味着 Agent Threat Model 不应继续假设：

```text
user sends prompt
→ model answers
→ session ends
```

更现实的模型是：

```text
persistent state
+
scheduler
+
credentials
+
tools
+
background execution
```

Agent State Store、Harness Credential 和 Scheduler 都已经成为 Security Asset。

# 5. Noise Filter

## “Prefix-aware Routing 一定降低延迟”

错误。

如果一个 Hot Prefix 对应大量流量，Affinity 会把请求集中到同一个 Worker。独立 H200 实验中，某个 Hot-prefix 场景的 Goodput 比 Load-aware Routing 低约 23%。([GitHub][6])

应该关注：

> Locality benefit − Queue penalty。

---

## “Agent Eval 只要用强模型做 Judge 就足够”

不够。

LLM Judge 适合开放式质量，但：

```text
是否调用错误 Tool
是否写错外部状态
是否违反权限
是否出现重复副作用
```

都更适合确定性检查。

AWS Reference 允许 Code-based Evaluator，并明确支持 Tool-call Trajectory Evaluation；这比单独 Answer Scoring 更接近生产要求。([Amazon Web Services, Inc.][2])

---

## “10,000 Agent 比 100 Agent 更聪明”

当前证据完全不足以支持这种一般性结论。

OpenAI 的案例是一个极高预算、极窄目标、拥有形式验证器的研究运行。它证明的是：

> 大规模搜索可以被工程化。

而不是：

> Agent 数量越多，任务效果单调提升。

([OpenAI][4])

---

## “Rust Kernel 就等于 GPU Memory Safety 已解决”

不成立。

Rust 能消除大量：

* aliasing；
* lifetime；
* ownership；

错误，但 GPU 仍然存在：

* Race；
* synchronization；
* numerical issue；
* FFI；
* unsafe block；
* compiler bug。

CUDA Rust 目前也远未达到 CUDA C++ 的生态成熟度。([NVIDIA Developer][3])

---

## “Microsoft 减少了大量 Ticket，因此 Agent 已证明产生因果收益”

需要降权。

Microsoft 报告的 Ticket、节省时间、覆盖率和用户满意度都是公司自己的运营指标，没有独立对照实验。([Microsoft][5])

真正可迁移的信号是架构：

```text
specialization
capability separation
fresh state
approval
outcome validation
```

而不是具体收益比例。

---

## “Semantic Model Router 已经可以完全自动决定最优模型”

GitHub 本周把 Project HydraFusion 放进 Copilot CLI `/experimental`，根据任务在 Local、Cloud 和 Compound Model 之间自动选择，目标同时考虑性能、成本与延迟。([The GitHub Blog][10])

这很值得跟踪，但仍属于 Experimental。

真正进入生产前，还需要回答：

* Router 的 Eval Ground Truth 是什么？
* 错误路由成本多高？
* Sensitive Data 是否允许 Cloud Escalation？
* Latency Prediction 是否稳定？
* Routing Policy 如何 Version / Rollback？

所以暂不把“自动模型路由”视为已解决问题。

# 本周工程结论

本周五个信号可以被放进同一张架构图：

```text
                         AI SYSTEM
                            │
             ┌──────────────┼──────────────┐
             ▼              ▼              ▼
      Inference Plane   Agent Plane    Control Plane
             │              │              │
        KV locality     Task search     Permissions
        Queue load      Tool trajectory Sandbox
        GPU kernels     Artifacts       Eval gate
        Routing         Verification    Approval
             │              │              │
             └──────────────┼──────────────┘
                            ▼
                       Evidence Plane
```

其中最明显的变化是：**越来越多“过去隐藏在实现内部的东西”正在成为显式系统状态。**

过去：

```text
KV Cache
= model server implementation detail
```

现在：

```text
KV Cache
= routing decision
```

过去：

```text
Agent tool sequence
= opaque reasoning trace
```

现在：

```text
Tool trajectory
= CI evaluation artifact
```

过去：

```text
Agent permission
= prompt / tool availability
```

现在：

```text
Permission
= user + device + operation + approval
```

过去：

```text
Multi-agent
= several agents talking
```

现在：

```text
Multi-agent
= distributed search + scheduling + artifact reduction + verifier
```

因此，本周最值得长期积累的五类能力是：

1. **Data-locality-aware Inference Scheduling**：理解 KV Cache、Queue 与 Placement 的联合优化。
2. **Agent Evaluation Engineering**：把行为回归、Tool Trace 和权限测试真正纳入 CI。
3. **GPU Systems Programming**：理解 Kernel、Memory Model 与安全抽象，而不只使用高层 Serving Framework。
4. **Distributed Agent Search**：把 Agent Orchestration 当成 Scheduling、Search 和 Artifact Management 问题。
5. **Capability-oriented Production Design**：围绕真实业务对象，把 Read、Suggest、Execute、Approve 和 Validate 分成独立权限。

如果本周只投入一段学习时间，优先建议做上面的 **KV-aware Routing 2 小时模拟实验**。它很小，但会把 Cache、Queueing、Routing、Tenant Isolation 和 GPU Serving 这几个原本容易分开理解的问题真正连在一起。
