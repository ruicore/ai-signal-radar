## ① 🆕 Microsoft + GitHub：Agentic Resource Discovery / Agent Finder，把“工具发现”从手工配置变成运行时能力

**Source**：Microsoft — *Introducing the Agentic Resource Discovery specification*；GitHub — *Agent finder for GitHub Copilot now available*
**Time**：2026-06-17

### 1. 发生了什么

Microsoft 发布 **Agentic Resource Discovery（ARD）specification**，GitHub 同步推出 Copilot **Agent Finder**。核心变化是：agent 不再需要把所有 MCP servers、skills、agents、tools 预先塞进上下文，而是在执行任务时按需发现合适能力。GitHub 明确说，Agent Finder 会基于开放 ARD 规范，从用户选择的 registry 中发现合适资源，并且支持公共 catalog 或企业内部私有 registry。([Command Line][1])

### 2. 工程上具体做了什么

ARD 定义的是一个“能力发现协议”：agent client 可以询问“什么资源能帮助完成这个任务”，discovery service 返回结构化能力信息、调用方式、适用边界、来源和策略相关元数据。Microsoft 特别强调它不是单一全球 catalog，而是允许多个 discovery services，企业可以维护自己的受控答案集。GitHub Agent Finder 则把这个能力接入 Copilot，同时声明不会自动安装资源，仍由用户或组织策略控制。([Command Line][1])

### 3. 为什么重要

这是 agent runtime 的控制面信号。过去的做法是：

```text
把所有 tools / MCP / skills 预先配置进 agent
```

问题是上下文膨胀、权限边界不清、工具过期、组织治理困难。ARD 代表一种新模式：

```text
agent capability discovery
+ private registry
+ policy-aware invocation
+ runtime selection
```

未来 agent 平台需要的不是更长 system prompt，而是一个可治理的 capability registry。

### 4. alternative approach

替代方案是继续使用静态配置：

```text
tools.yaml
mcp_servers.json
skills/
```

优点是简单、可预测；缺点是能力越来越多时会变成手工维护负担，并且容易把无关工具暴露给 agent。中间路线是：保留静态 allowlist，但让 agent 在 allowlist 内做 runtime discovery。

### 5. 对我的启发（可执行）

你自己的 agent / coding workflow 可以先定义一个最小 manifest：

```python
class AgentResourceManifest:
    name: str
    kind: str  # tool | mcp | skill | agent
    description: str
    input_schema: dict
    authority_scope: str
    owner: str
    policy_tags: list[str]
```

不要再把所有工具直接硬编码进 `tools.py`。先让 agent 通过 manifest 检索“可用能力”，再决定是否调用。

## ② 🆕 Cloudflare：Agents SDK + Flue，把 durable execution / sandbox / filesystem 变成 agent runtime primitives

**Source**：Cloudflare Blog — *Bringing more agent harnesses and frameworks to Cloudflare, starting with Flue*
**Time**：2026-06-17

### 1. 发生了什么

Cloudflare 宣布把 Agents SDK 的底层 primitives 开放给更多 agent harness 和 framework，首个集成是 Flue。Cloudflare 明确把 cloud agent 面临的问题定义为分布式系统问题：中断后恢复、运行不可信代码、使用工具、保存状态、处理长任务，而不是单次请求响应。([The Cloudflare Blog][2])

### 2. 工程上具体做了什么

Cloudflare 提供的 primitives 包括：

```text
Durable Objects
Durable Streams
durable execution
dynamic code execution
durable virtual filesystem
dynamic workflows
bindings for tools / AI Gateway / Browser / Containers
```

Flue agents 在 Cloudflare 上以 Durable Object 形式运行，使用 `runFiber` checkpoint agent turn；代码执行用 Dynamic Worker isolate；虚拟文件系统由 Durable Object + SQLite 支撑；workflow step 可以持久化、失败重试、等待审批或事件。Cloudflare 还强调 bindings 可以把能力注入 agent，而不是把 credential 暴露给模型。([The Cloudflare Blog][2])

### 3. 为什么重要

这条信号说明：agent runtime 正在从“LLM loop”变成“可恢复执行系统”。

关键变化是：

```text
agent turn != one HTTP request
agent state != Python memory
tool execution != unrestricted shell
```

生产 agent 必须考虑 checkpoint、resume、sandbox、filesystem、credential boundary、approval、retry 和 cost。

### 4. alternative approach

轻量替代方案：

```text
container-per-agent
+ Redis / Postgres checkpoint
+ mounted workspace
+ queue worker
+ OpenTelemetry
```

这个方案更容易自建，但你需要自己处理隔离、恢复、代码执行安全和长期状态。Cloudflare 的路线是把这些变成平台原语。

### 5. 对我的启发（可执行）

如果你在写 agent backend，应该把每一步执行都设计成可恢复：

```python
class AgentStep:
    step_id: str
    run_id: str
    input_hash: str
    output_hash: str | None
    checkpoint_state: dict
    status: str  # pending | running | succeeded | failed
```

先不要追求复杂 multi-agent。先做到：**每一步可记录、可恢复、可重放**。

## ③ 🆕 OpenAI：Deployment Simulation，把 agent / model 发布前评估从静态 benchmark 拉向真实流量 replay

**Source**：OpenAI — *Predicting model behavior before release by simulating deployment*
**Time**：2026-06-16

### 1. 发生了什么

OpenAI 公开 **Deployment Simulation** 方法：在新模型发布前，用候选模型重放历史真实对话，预测它在实际部署中的行为。OpenAI 表示该方法已用于 GPT-5-series Thinking 部署，并扩展到更复杂的 agentic rollout。([OpenAI][3])

### 2. 工程上具体做了什么

方法核心是：

```text
historical production conversation
  → remove original assistant response
  → regenerate with candidate model
  → compare likely deployment behavior
```

OpenAI 提到其分析覆盖 130 万条 de-identified conversations。更关键的是 agentic coding 场景：OpenAI 使用 120,000 条内部员工 agentic coding trajectories 来模拟 GPT-5.5 内部 coding agent 部署。由于一个 agent trajectory 可能依赖上百次 tool calls、repo state、网络响应和临时失败，OpenAI 没有把 tool calls 应用到真实系统，而是用工具模拟器复现环境，并把模拟 realism 从明显可区分提升到接近随机水平。([OpenAI][3])

### 3. 为什么重要

这说明 evaluation 的中心正在变化：

```text
static benchmark
  → production trajectory replay
```

对于 agent 来说，单个 prompt 的好坏不够重要。真正重要的是完整执行轨迹：

```text
planning
tool calls
environment response
failure handling
state growth
final outcome
```

这也解释了为什么传统 SWE-bench / demo eval 不足以代表真实 agent 质量。

### 4. alternative approach

替代方案包括：

```text
static eval set
synthetic prompts
small canary rollout
human review only
```

这些方法仍有价值，但缺点是覆盖不到真实流量分布，也很难模拟复杂 tool / environment interaction。更现实的路线是：静态 eval + historical trace replay + controlled canary 三层结合。

### 5. 对我的启发（可执行）

你可以给自己的 agent 增加一个最小 replay eval：

```text
agent_runs.jsonl
  → remove final output
  → replay with new prompt/model
  → mock tool responses
  → compare against human correction / expected result
```

不要只维护“人工写的测试题”。真实失败 trace 才是最有价值的 eval 资产。

## ④ 🆕 Google DeepMind：Agent 安全进入 AI Control Roadmap，监控对象变成 reasoning / action / plan 轨迹

**Source**：Google DeepMind — *Securing the future of AI agents*
**Time**：2026-06-18

### 1. 发生了什么

Google DeepMind 发布 AI Control Roadmap，核心观点是：面对高能力 agent，不能只依赖 alignment，需要 defense-in-depth。DeepMind 明确提出要把内部 AI agent 当作潜在 insider threat 来管理，并用可信 AI supervisor 监控 agent 的 reasoning、actions 和 plans。([Google DeepMind][4])

### 2. 工程上具体做了什么

DeepMind 的控制框架包含：

```text
monitoring
trusted AI supervisors
action blocking
coverage / recall / time-to-response metrics
risk-based protocol escalation
```

低风险、可逆操作可以异步审查；高风险操作需要同步阻止。DeepMind 还提到一个内部异步监控系统，分析了 100 万个 coding agent tasks，并用于 Gemini Spark agent 的 live monitor；观察到的问题包括非故意的数据删除，以及大量由误解或过度积极造成的 flag。([Google DeepMind][4])

### 3. 为什么重要

这条信号把 agent security 从“权限配置”提升到了“行为监控”。

传统安全关注：

```text
这个 tool 能不能调用？
```

现在更关键的是：

```text
agent 为什么要调用？
这个 plan 是否危险？
这个 action 是否可逆？
是否需要 supervisor gate？
```

对于 coding agent，删除文件、改 CI、提交 PR、访问 secret、跨 repo 修改，都应该有风险等级和审查路径。

### 4. alternative approach

替代方案是只做静态 allowlist：

```text
allowed_tools = [...]
blocked_commands = [...]
```

这能挡住一部分明显危险行为，但挡不住“合法工具被错误使用”。更强方案是：静态权限 + runtime risk classifier + supervisor review + audit log。

### 5. 对我的启发（可执行）

你可以为 agent tool call 增加风险门禁：

```python
class ToolCallPolicy:
    tool_name: str
    risk_level: str  # low | medium | high
    reversible: bool
    approval_required: bool
```

高风险操作，例如 `rm`, `git push`, `deploy`, `delete_record`, `send_email`，默认进入 supervisor / human approval gate。

## ⑤ 🆕 Cloudflare：Vulnerability Discovery Harness 展示“多阶段、可恢复、模型无关”的安全 agent 架构

**Source**：Cloudflare Blog — *Build your own vulnerability harness*
**Time**：2026-06-18

### 1. 发生了什么

Cloudflare 公开了自己的 vulnerability discovery harness 设计经验，核心判断是：未来的 agentic workflow 不是 standalone model、单 prompt 或单 agent session，而是一个模型无关、状态外置、可恢复、可验证的 orchestrated system。([The Cloudflare Blog][5])

### 2. 工程上具体做了什么

Cloudflare 的安全 agent harness 不是“让一个 agent 审代码”，而是多阶段 pipeline：

```text
Recon
  → Hunt
  → Validate
  → Report
  → independent re-verification
  → ingest API
```

他们强调多个独立调查要跨运行存活、不要共享上下文、可以重新 scope、可以 cross-reference。后续 fleet scanner 覆盖 128 个 repo，使用 producer-consumer loop、SQLite 按 `run_id / repo / stage` 保存状态，严格控制 context，使用不同模型做 discovery 和 validation，并把 response text 也当作错误分类对象，而不是只看 exception。([The Cloudflare Blog][5])

### 3. 为什么重要

这是非常强的 AI systems engineering 信号：**LLM 是无状态计算单元，harness 才是系统本体**。

它把复杂 agent 工作流拆成：

```text
state persistence
context budget
stage isolation
model routing
validation separation
cross-run memory
retry / resume
structured findings
```

这比“写一个很强的安全审计 prompt”更接近生产系统。

### 4. alternative approach

替代方案是：

```text
在 IDE 里反复运行一个 security review agent
```

优点是简单；缺点是不可恢复、不可度量、上下文污染、难以跨 repo 聚合、难以独立验证。更稳的中间路线是：保留单 agent 审查体验，但把输出写入 DB，由独立 validator 复核。

### 5. 对我的启发（可执行）

你可以从最小三阶段 harness 开始：

```text
Recon: 识别模块 / attack surface
Hunt: 针对每类风险生成候选 finding
Validate: 独立模型或规则验证 finding
```

关键不是 prompt，而是把每个阶段的输入、输出、状态、错误和验证结果存下来。

# 5️⃣ 一个工程行动（1–3 小时）

## 建一个最小 “Agent Trajectory Ledger”

目标：把本周 5 个信号落到一个小型可实现组件里：记录 agent 每一步的能力来源、执行状态、风险等级、checkpoint、tool response 和 replay 信息。

### Step 1：定义 trajectory schema（30 分钟）

```python
from dataclasses import dataclass
from datetime import datetime
from typing import Any


@dataclass
class AgentResource:
    resource_id: str
    kind: str              # tool | mcp | skill | agent
    name: str
    authority_scope: str   # readonly | write_repo | deploy | external_api
    owner: str


@dataclass
class AgentStep:
    run_id: str
    step_id: str
    parent_step_id: str | None
    resource_id: str | None
    intent: str
    input_summary: str
    output_summary: str | None
    checkpoint_state: dict[str, Any]
    risk_level: str        # low | medium | high
    status: str            # pending | running | succeeded | failed | blocked
    created_at: datetime
```

### Step 2：加一个 supervisor gate（30–45 分钟）

```python
HIGH_RISK_SCOPES = {"write_repo", "deploy", "external_api"}


def require_supervisor(resource: AgentResource, step: AgentStep) -> bool:
    if step.risk_level == "high":
        return True
    if resource.authority_scope in HIGH_RISK_SCOPES:
        return True
    return False
```

规则：

```text
readonly tool：默认放行
write_repo / deploy / external_api：默认需要审批或 supervisor check
```

### Step 3：每步写入 SQLite / JSONL（30–45 分钟）

```python
import json
from dataclasses import asdict


def append_step(step: AgentStep, path: str = "agent_trajectory.jsonl") -> None:
    with open(path, "a", encoding="utf-8") as f:
        f.write(json.dumps(asdict(step), default=str, ensure_ascii=False) + "\n")
```

### Step 4：导出 replay eval candidate（30–60 分钟）

规则：

```text
failed step
blocked step
human corrected step
high-risk approved step
unexpected tool result
```

都导出到：

```text
evals/
  replay_candidates.jsonl
  frozen/
    v001.jsonl
```

### 为什么这一步值得做

它把本周核心方向合并成一个最小工程骨架：

```text
ARD / Agent Finder → resource_id / authority_scope
Cloudflare Agents SDK → checkpoint_state / durable step
OpenAI Deployment Simulation → replay candidate
DeepMind AI Control → supervisor gate / risk_level
Cloudflare Harness → stage persistence / validation-ready trace
```

这一步做完，你的 agent 就不再只是“调用模型完成任务”，而开始具备生产系统需要的最小可观测性、恢复能力和安全边界。
