# AI Systems Engineering 技术雷达（高信号版）

**观察窗口：2026 年 8 月 3 日—8 月 9 日**

本周筛选后保留 **5 个技术信号**。它们分别来自实时推理、Agent Runtime Governance、训练与评估基础设施、LLM Serving Observability，以及推理编译。共同指向一个越来越清楚的架构变化：

> **AI Systems 正在从“围绕模型构建应用”，进入“把模型嵌入具有确定性边界、持续状态、运行时策略和系统级验证的软件基础设施”。**

---

# 1. Executive Summary

* **本周最值得关注的是 OpenAI GPT‑Live 暴露出的实时 AI 架构范式：把不可阻塞的交互路径与高延迟推理、Tool Use 和持久化彻底解耦。** Voice 只是第一个明显场景。其核心模式是 `Realtime Fast Path + Async Intelligence Path`：媒体流持续运行，复杂推理异步完成；Context Compaction、实例迁移甚至更换模型都被处理为后台状态迁移。这个架构很可能迁移到机器人、Computer Use、实时协作和其他持续运行 Agent。([OpenAI][1])
* **Agent 安全正在从“每次 Tool Call 是否允许”升级为“整个 Action Sequence 是否合法”。** AWS 发布的 Dogwood 在 Cedar 点时授权之上增加 Temporal Policy，可表达“必须先审批才能执行”“过去一小时累计金额不得超过 X”“读取敏感数据后不能再访问外部系统”等跨调用约束。它目前只是 Reference Interpreter，但这个抽象很重要：生产 Agent Governance 需要 Stateful Policy，而不仅是 RBAC。([Amazon Web Services, Inc.][2])
* **Agent Training / Evaluation 的关键基础设施正在下沉为独立 Environment Service。** Microsoft Orchard 把 Sandbox 从某个训练框架的内部实现抽出来，变成 Kubernetes-native 的公共执行层，同一个环境同时服务 Trajectory Collection、RL Rollout 和 Evaluation，并允许直接在 Codex、OpenClaw 等真实 Harness 内训练。长期看，这比“又一个 Agent Framework”重要得多，因为它处理的是 train–deploy mismatch。([Microsoft][3])
* **LLM Serving Observability 开始补齐传统 APM 无法覆盖的 GPU 垂直调用链。** TELLER 把 vLLM/SGLang 层、Python/C++、CUDA Runtime、GPU Kernel、NCCL 和日志重新关联到单个请求，说明未来推理平台的 Trace 不会停在 HTTP Span，而需要跨越 Scheduler → CUDA Launch → Kernel → Collective。([arXiv][4])
* **LLM 正开始进入系统软件内部，但可靠模式不是“让模型自由写 CUDA”。** AgentCompile 的关键设计是让 LLM 在 Compiler-defined Contract 内提供建议或生成 Kernel，随后必须经过编译、数值正确性、性能 Benchmark 和 Fallback Gate。这种 **Generate → Verify → Measure → Admit** 的模式，比具体的 CUDA 性能数字更值得长期关注。([arXiv][5])

# 2. Top 5 AI Systems Signals

## Signal 1：Realtime AI 正从 Request/Response 系统变成持续运行的 Stateful Stream Processor

**Source:** OpenAI — *How we built a realtime system for responsive voice AI in six months*
**Date:** 2026-08-03
**Evidence Level:** **Official**
**Technology Maturity:** **Production Adoption**

### 1. 发生了什么

GPT‑Live 不再采用传统：

```text
Audio
→ Turn Detection
→ STT / Model
→ TTS
→ Audio
```

而是让 Voice Model 进行 Full-duplex Continuous Inference：音频持续进入和离开模型，更深的推理、搜索和 Tool Use 通过另外一条异步路径执行。OpenAI 明确将 Media Flow 与 Application / Business Logic 分离，使慢 Tool 或后端服务不会阻塞实时媒体链路。([OpenAI][1])

一个非常值得注意的生产细节是，OpenAI 将媒体前端和推理逻辑从 Python `asyncio` 改写为 Go 后，新系统的 **p95 Frame Delivery 达到了旧系统 p50 的水平**。这不是“Go 比 Python 快”的一般性结论，而是说明在具有严格 Frame Deadline 的持续流场景中，Runtime Jitter 本身会成为架构问题。([OpenAI][1])

### 2. 工程上改变了什么

普通 LLM 应用优化的是：

```text
Request
→ TTFT
→ TPOT
→ Response
```

实时 AI 系统需要优化：

```text
Continuous Session

Media Fast Path
│
├── frame deadline
├── jitter
├── packet loss
└── continuous inference

Async Intelligence Path
│
├── reasoning
├── search
├── tools
└── persistence
```

也就是说，**Latency 已经不是一个 Request Metric，而是一组相互依赖的 Deadline Budget。**

这与传统实时系统、视频会议、在线游戏的架构更接近，而不是普通 Web API。

### 3. Architecture impact

最值得学习的是 **Fast Path / Slow Path Separation**。

GPT‑Live 将需要实时保证的组件保持尽可能小，而把：

* Tool Call
* Frontier Model Delegation
* Persistence
* Context Compaction
* Model Instance Migration

全部移出 Critical Path。([OpenAI][1])

更有意思的是 Context Compaction。Compaction 会改变历史 Context，因此原来的 KV Cache 会失效。OpenAI 没有暂停当前 Session 等待重建，而是：

```text
Current Instance
     │
     │ continues serving
     │
     ├───────────────┐
                     │
              compact context
                     │
              warm new instance
                     │
                 prefill
                     │
                     ▼
Current Instance ── cutover ──> Replacement Instance
```

这实际上是 **Blue/Green Deployment 思想在 Stateful Inference Session 中的应用**。([OpenAI][1])

### 4. Alternative approach 和 trade-off

| Architecture                                | 优势       | 代价                             |
| ------------------------------------------- | -------- | ------------------------------ |
| STT → LLM → TTS Cascade                     | 组件简单、易调试 | 串行延迟高，丢失语音语义                   |
| Turn-based Speech-to-Speech                 | 较低延迟     | 仍依赖 Turn Detector              |
| Full-duplex Single Model                    | 极低交互延迟   | 深推理能力和成本受限                     |
| **Fast Voice Model + Async Frontier Model** | 响应性与智能解耦 | Session State、同步、Delegation 复杂 |
| 所有能力放在单模型                                   | 架构简单     | Critical Path 过重               |

OpenAI 同时提前 Prefill Frontier Model Session，并保持 Session Affinity 和 Prompt Cache，从而减少真正发生 Delegation 时的等待时间。([OpenAI][1])

### 5. 对 AI Systems Engineer 的启发

一个很强的通用原则是：

> **不要让高智能路径成为实时体验的同步依赖。**

未来构建：

* Voice Agent
* Robot Interaction
* Computer Control
* Collaborative Agent
* Live Assistant

时，应分别定义：

```text
Realtime SLA
Reasoning SLA
Tool SLA
Persistence SLA
```

而不是把它们压成一个 Endpoint 的 `P95 latency`。

OpenAI 的生产 Shadow Testing 也值得直接借鉴：它让新系统在真实 Voice Session 上执行只读 Shadow Inference，发现真实瓶颈首先出现在 CPU Stream Handler、Queue 和 Network，而不是 GPU。([OpenAI][1])

# Signal 2：Agent Policy 从 Point-in-Time Authorization 进入 Temporal Runtime Verification

**Source:** AWS / Dogwood
**Date:** 2026-08-06
**Evidence Level:** **Official / Reproducible Engineering Practice**
**Technology Maturity:** **Open Source Experiment**

### 1. 发生了什么

AWS 开源 **Dogwood**，这是一个为 Agent Tool Use 设计的 Governance Language。

已有 Cedar Policy 擅长处理：

```text
Can principal X
perform action Y
on resource Z
right now?
```

Dogwood增加的是：

```text
Given what this agent has already done,
is action Y still allowed?
```

因此可以表达：

* 一小时内必须存在有效审批；
* 过去一小时最多调用某工具 N 次；
* 累计转账不得超过 $5,000；
* 最多操作三个不同 Recipient；
* 访问敏感信息之后禁止调用某些外部工具。([Amazon Web Services, Inc.][2])

### 2. 工程上改变了什么

普通 IAM 可以被抽象为：

```text
decision = policy(current_request)
```

Dogwood 类系统变成：

```text
decision =
    policy(
        current_request,
        recent_event_history
    )
```

这看似只是多加一份 History，实际上会引入完整的 Stateful Systems 问题：

* Event Ordering
* Timestamp Trust
* Concurrent Tool Calls
* Durable History
* Window Eviction
* Multi-tenancy
* Replay
* Crash Recovery

AWS 特别指出，Rate Limit 若统计 **response** 而不是 **request**，Agent 可以并发发起大量请求，在任何 Response 返回之前绕过限制。([Amazon Web Services, Inc.][2])

这是非常典型的 Distributed Systems Race Condition，而不是 Prompt Engineering 问题。

### 3. Architecture impact

生产版本可能形成：

```text
Agent
  │
  ▼
Tool Gateway
  │
  ├── Current Request
  │
  ├── Identity
  │
  └── Event History
          │
          ▼
Temporal Policy Engine
          │
      ALLOW / DENY
          │
          ▼
        Tool
```

Policy Engine 因此会成为：

> **Agent Runtime 的 Stateful Control Plane。**

它需要与 Tool Execution Path 保持强一致语义，否则“Policy 判断过的 Action”和“实际执行的 Action”之间可能发生 TOCTOU 问题。

### 4. Alternative approach 和 trade-off

| 方法                                | 优点                    | 局限               |
| --------------------------------- | --------------------- | ---------------- |
| Prompt Policy                     | 最简单                   | 无强制能力            |
| RBAC / ABAC                       | 成熟、快速                 | 不理解行为序列          |
| Approval per action               | 风险低                   | Human bottleneck |
| Static Workflow DAG               | 顺序明确                  | 动态性差             |
| **Temporal Policy**               | 保留 Agent 自主性，同时限制行为历史 | Stateful、并发语义复杂  |
| Full formal workflow verification | 保证强                   | 实现和建模成本高         |

Dogwood 本身明确说明其当前 Reference Interpreter **不应直接用于生产 Authorization**；Event Authentication、Timestamp Integrity、Trace Durability、Multi-tenant Isolation、Provider Sandbox 和 Audit Logging 均需要生产实现另行解决。([GitHub][6])

### 5. 对 AI Systems Engineer 的启发

Agent Runtime 不应只问：

> 这个 Tool 可不可以调用？

而要问：

> **在这个 Task 的当前历史状态下，这个 Tool 还可不可以调用？**

这会逐渐形成新的 Policy Primitive：

```text
Identity
+ Current Action
+ Task
+ Historical Actions
+ Accumulated Exposure
+ Remaining Capability
```

它与 Cloudflare 本周提出的 Agent Access Model 中 **Trust Ratchet** 思路高度一致：随着 Agent 接触更多受保护数据，其剩余 Capability 只能缩小，而不能在同一个 Task 中重新扩大。([Cloudflare Blog][7])

# Signal 3：Environment Layer 正成为 Agent Training 与 Evaluation 的共享基础设施

**Source:** Microsoft Research — Orchard
**Date:** 2026-08-03
**Evidence Level:** **Official / Reproducible Engineering Practice**
**Technology Maturity:** **Open Source Experiment**

### 1. 发生了什么

Microsoft 开源 **Orchard**。

其核心不是一个新的 Agent Loop，而是 **Orchard Env**：一个 Kubernetes-native Environment Service，用统一环境运行：

* Software Engineering Agent
* Browser Agent
* GUI Agent
* Personal Assistant

并复用在：

```text
Data Collection
→ SFT
→ RL Rollout
→ Evaluation
```

整个生命周期。([Microsoft][3])

### 2. 工程上改变了什么

很多 Agent Research Stack 当前是：

```text
Benchmark A
└── custom sandbox

Training Pipeline
└── another sandbox

Evaluation
└── another runtime

Production Harness
└── completely different environment
```

于是产生经典问题：

> **Train / Eval / Deploy 环境不一致。**

Orchard 的做法是：

```text
                  ┌─ Data Collection
                  │
                  ├─ SFT
Orchard Env ──────┼─ RL Rollout
                  │
                  ├─ Evaluation
                  │
                  └─ Real Agent Harness
```

Environment 成为共享基础设施，而不是 Trainer 的内部 implementation detail。([GitHub][8])

### 3. Architecture impact

这个方向值得特别重视，因为 Agent Evaluation 与普通 Model Eval 的一个根本差别是：

> **Environment 是 Evaluation 的一部分。**

一个 SWE Agent 的成绩可能受：

* Container 初始化；
* Network 状态；
* Repository Snapshot；
* Tool Version；
* Harness；
* Retry Policy；
* Timeout；

影响。

因此未来 Evaluation Artifact 可能需要包含：

```text
Model Version
Harness Version
Environment Image
Task Snapshot
Tool Version
Policy
Reward
Trajectory
```

而不是只有：

```text
model + benchmark score
```

Orchard 甚至允许 Agent 在实际部署 Harness 内训练：Proxy 记录 Harness 自己的 Model Call，并将其转换为训练样本，从而降低 simplified training loop 与 production harness 的 mismatch。([Microsoft][3])

### 4. Alternative approach 和 trade-off

| 方法                               | 优势                | 局限                    |
| -------------------------------- | ----------------- | --------------------- |
| Benchmark-specific Environment   | 简单、针对性高           | 难复用                   |
| Local Docker Sandbox             | 开发方便              | 大规模 Rollout 能力有限      |
| VM-per-task                      | 强隔离               | 启动和成本高                |
| Hosted proprietary sandbox       | 开箱即用              | Reproducibility 与控制较弱 |
| **Reusable Environment Service** | Train/Eval 统一、规模化 | Control Plane 复杂      |

### 5. 对 AI Systems Engineer 的启发

值得长期掌握的并不是 Orchard API，而是 **Environment-as-Infrastructure** 这个抽象。

Agent Platform 可能需要一个类似：

```text
Environment Control Plane
├── Provision
├── Snapshot
├── Reset
├── Network Policy
├── Secret Injection
├── File IO
├── Tool Gateway
├── Execution
└── Evidence Collection
```

的服务。

微软报告 Orchard-SWE 使用约 3B Active Parameters 的模型达到 69.7% SWE-bench Verified，并在 Value Model Reranking 后达到 73.0%；这些结果是项目团队自身实验，值得关注，但应将其与 Environment 架构价值分开看待。([Microsoft][3])

# Signal 4：LLM Serving Observability 正从 GPU Profiler 走向 Request-level Cross-layer Trace

**Source:** TELLER — Sun Yat-sen University，ASE 2026
**Date:** 2026-08-03
**Evidence Level:** **Reproducible Engineering Practice**
**Technology Maturity:** **Demo**

### 1. 发生了什么

TELLER 试图解决一个越来越明显的问题：

普通 APM 能告诉你：

```text
POST /generate = 8.2 s
```

GPU Profiler 能告诉你：

```text
kernel X = 3.4 ms
NCCL AllReduce = 12 ms
```

但发生 Incident 时，工程师真正需要知道的是：

> **哪个 Request，在哪一层，从哪个 Operation 开始异常？**

TELLER 通过 NVTX、CUPTI 和 Service Log，构建跨：

```text
Inference Engine
↓
Framework / Backend
↓
CUDA Runtime
↓
GPU Kernel
↓
NCCL / Network
```

的 Request-level Call Chain。([arXiv][4])

### 2. 工程上改变了什么

LLM Inference 与普通 Web Backend 一个重要区别是：

```text
1 HTTP request
≠
1 independent execution path
```

Continuous Batching 会把多个 Request 合并进同一次 GPU Execution。

同时存在：

* Coroutine Scheduling
* Async CUDA Launch
* Kernel Fusion
* Tensor Parallelism
* NCCL Collective
* Shared KV Cache

因此传统：

```text
trace_id → span tree
```

并不足够。

需要恢复：

```text
Logical Request
↕
Scheduler Step
↕
Batch
↕
Host Launch
↕
GPU Kernel
↕
Communication
```

之间的映射。([arXiv][4])

### 3. Architecture impact

TELLER 一个很好的设计是将系统拆成两阶段：

```text
Stage 1: Deterministic evidence construction

Raw Trace
+ Logs
→ Request-level Call Chain
→ Candidate Localization

Stage 2: Learned diagnosis

Compact Causal Slice
+ Logs
→ Root Cause Reasoning
```

也就是说：

> **让确定性系统负责构造 Evidence，让模型负责解释 Evidence。**

这比把几 MB Raw Trace 直接丢给 LLM 更符合生产系统设计。

其 Trace Pair Encoding 通过保留 Parent、Depth、Duration 等结构信息，将 Trace 长度压缩超过 80%，同时保持较好的诊断表现；这些数据来自论文实验，尚不能等同生产验证。([arXiv][4])

### 4. Alternative approach 和 trade-off

| 方法                              | 优势                  | 局限                    |
| ------------------------------- | ------------------- | --------------------- |
| Logs                            | 低成本                 | 缺执行结构                 |
| GPU Profiler                    | 底层信息完整              | 难关联业务 Request         |
| OpenTelemetry                   | 请求语义清楚              | GPU 内部通常不可见           |
| Full Trace Capture              | 诊断能力强               | 成本巨大                  |
| **Selective Cross-layer Trace** | 请求语义 + GPU Evidence | Instrumentation 和关联复杂 |
| LLM over raw logs               | 快速实现                | 缺可靠 Evidence          |

### 5. 对 AI Systems Engineer 的启发

未来 Serving Observability 至少需要理解：

```text
Request
Session
Batch
Scheduler Step
Model Forward
CUDA Launch
Kernel
Collective
GPU
Node
```

这些实体之间的 Correlation。

一个非常值得持续关注的方向是：

> **LLM Serving 的“Distributed Tracing”最终会延伸到 GPU Execution Graph。**

这很可能成为 AI Infra 与传统 Observability 之间的新专业领域。

# Signal 5：LLM 开始参与生成系统级优化，但 Admission Gate 比生成能力更重要

**Source:** *AgentCompile: An LLM-Guided Compiler for Direct CUDA Inference*
**Date:** 2026-08-03，v2
**Evidence Level:** **Reproducible Engineering Practice**
**Technology Maturity:** **Open Source Experiment**

### 1. 发生了什么

AgentCompile 将 LLM 用在两层：

第一层：

```text
Compiler constructs candidates
→ LLM advises
→ Compiler generates
```

LLM 只负责：

* Semantic Label
* Candidate Priority
* Parameter Hint

第二层才允许 LLM 直接生成 CUDA Kernel，但范围被限定在五类 Decode-critical Fusion Pattern 中。([arXiv][5])

任何 LLM-generated Kernel 都必须经过：

```text
Compile
→ Interface Check
→ Numerical Verification
→ Runtime Benchmark
→ Performance Admission
→ Deploy

otherwise
→ Fallback
```

Repository 中甚至明确设置了 measured admission margin，失败 Candidate 会退回已有实现。([GitHub][9])

### 2. 工程上改变了什么

这与常见的：

> “让 Agent 优化 CUDA”

非常不同。

关键思想是：

> **LLM 不拥有最终 Authority。**

Compiler 和 Benchmark Harness 才拥有 Authority。

这是一种典型的：

```text
Probabilistic Proposal
+
Deterministic Verification
```

架构。

### 3. Architecture impact

它可能推广到：

```text
LLM
↓
Candidate Generator

          Compiler
          Tests
Candidate → Numeric Validator
          Benchmark
          Policy
             ↓
         Admission
```

未来 LLM 可能进入：

* Query Optimizer
* Compiler
* Scheduler
* Index Advisor
* Storage Planner
* Kernel Generator

但只有在存在强 Validation Oracle 的领域最可靠。

### 4. Alternative approach 和 trade-off

| Approach                                  | 优势             | 局限               |
| ----------------------------------------- | -------------- | ---------------- |
| 手写 CUDA Kernel                            | 最高可控性          | 人力成本高            |
| Template Compiler                         | 安全、可复现         | Search Space 有限  |
| Auto-tuning                               | 性能导向           | 难产生新实现           |
| Free-form LLM Kernel                      | Search Space 大 | Correctness 风险极高 |
| **LLM + Contract + Validator + Fallback** | 创造性与安全性折中      | Verification 成本高 |

论文报告其 Serving Runtime 相比 vLLM 在所测 Workload 上获得约 **1.04–1.16×** 的性能提升，而相对 PyTorch eager 的提升更大；但代码仓库目前是匿名论文 Artifact，只有少量 Commit，作者也明确定位为 Research Prototype，因此目前不应将性能结果外推到生产环境。([arXiv][5])

### 5. 对 AI Systems Engineer 的启发

非常值得抽象成：

> **不要问“LLM 能不能生成这个系统组件”，而要问“这个领域有没有足够强的 Oracle，让生成结果可以自动被拒绝”。**

适合 LLM 深度参与的系统领域往往有：

* Compiler
* Type Checker
* Unit Test
* Numerical Equivalence
* Benchmark
* Simulator
* Formal Policy

作为 Validation Oracle。

这是比“Agent 写了多少代码”更重要的技术方向。

# 3. Deep Dive Recommendation（技术精读）

## Original Source

**Title:** *Introducing Dogwood: runtime verification for AI agents*
**Author:** Marc Brooker, Joseph Tassarotti, Jean-Baptiste Tristan
**Organization:** AWS
**Date:** 2026-08-06
**Type:** Official Open-source Engineering Article + Reference Implementation

**Original URL:**
`https://aws.amazon.com/blogs/opensource/introducing-dogwood-runtime-verification-for-ai-agents/`

**Repository:**
`https://github.com/dogwood-policy/dogwood`

([Amazon Web Services, Inc.][2])

## Why This One

本周几个信号中，Dogwood 最值得亲手研究，因为它把一个容易被误认为“Agent Safety”的问题，变成了标准的软件系统问题：

```text
Event Stream
+
Policy Language
+
State
+
Concurrency
+
Authorization
```

它实际上连接了：

* IAM
* Complex Event Processing
* Runtime Verification
* Distributed Systems
* Agent Tool Use

并且 Reference Implementation 很小，1—3 小时就可以真正跑起来。

更重要的是，它让一个关键边界变得清晰：

> **Model 决定“我想做什么”，Runtime 决定“历史状态是否允许你这么做”。**

---

## Reading Guide

### 第一部分：先读 AWS 文章中的三个场景

重点理解：

**Prerequisite Policy**

```text
Approve
before
Sell
```

**Windowed Limit**

```text
sum(transfers in last 1h) <= limit
```

**Post-exposure Restriction**

```text
after accessing confidential information
external actions become unavailable
```

尤其认真看 AWS 对并发请求的讨论：为什么统计 `response` 会产生 Race Condition，而统计 `request` 才能真正限制并发累计金额。([Amazon Web Services, Inc.][2])

### 第二部分：看 Repository Layout

优先阅读：

```text

```

其中：

* `dogwood-language/`：Parser、Interpreter、Lowering；

* `dogwood-docs/examples/`：最适合快速理解行为；

### 第三部分：必须看 Security Considerations

这是整个 Repo 最有工程价值的部分之一。

作者明确列出了 Production Engine 仍需要处理：

* Trusted Timestamp
* Event Authentication
* Event Field Consistency
* Durable Trace
* Multi-tenancy
* Provider Script Limits
* Audit Logging
* Error Information Leakage。([GitHub][6])

这些限制实际上就是：

> 从 Research Policy Language 到 Production Authorization Service 的 Architecture Backlog。

## Practical Experiment：实现一个 Stateful Agent Tool Policy

**预计时间：1.5—2.5 小时**

### 目标

构建一个最小实验，证明：

> Stateless IAM 无法表达的 Agent 行为约束，可以通过 Temporal Policy 精确控制。

### 场景

定义三个 Tool：

```text
read_sensitive_data()
request_external_send(payload)
approve_external_send(payload_hash)
```

Policy：

```text
1. 默认可以读取 sensitive data。

2. external_send 必须存在：
   最近 10 分钟，
   对同一个 payload_hash 的 approval。

3. 一旦读取 sensitive data，
   external_send 永久禁止，
   直到新 Task 开始。

4. 每个 Task 最多允许 3 次 external_send。
```

### 步骤

使用 Dogwood CLI：

```bash
dogwood validate
dogwood replay
dogwood lower
```

分别构造四条 Trace：

```text
A:
approval
send
→ ALLOW

B:
send
→ DENY

C:
approval
read_sensitive
send
→ DENY

D:
approval
send × 4
→ fourth DENY
```

然后增加一个并发案例：

```text
send request #1
send request #2
send request #3
send request #4
```

观察基于：

```text
request history
```

与：

```text
response history
```

进行限流时行为有何不同。

### 验证方式

实验不是只看：

```text
ALLOW / DENY
```

而应记录：

| Case                  | Expected | Actual | Policy reason |
| --------------------- | -------- | ------ | ------------- |
| valid approval        | ALLOW    |        |               |
| missing approval      | DENY     |        |               |
| post-sensitive access | DENY     |        |               |
| rate limit            | DENY     |        |               |
| concurrent race       | DENY     |        |               |

最后回答：

> 如果 Event Store Crash 丢失最近 5 分钟事件，这个 Policy 会 Fail-open 还是 Fail-closed？

这一步会把实验从“试一个 Policy DSL”提升成真正的 Systems Exercise。

# 4. Research Direction

## 4.1 Realtime AI 会形成独立于普通 LLM Backend 的架构分支

GPT‑Live 显示，Realtime AI 的核心约束已经变成：

```text
continuous session
frame deadline
state migration
regional routing
jitter
reconnect
background reasoning
```

而不是简单 TTFT。

OpenAI甚至为 WebRTC 设计 WARP，将媒体和 Data Channel 初始化所需的网络往返从六次压缩到一次，并让 libwebrtc 与 Pion 开始支持相关方案。([OpenAI][1])

长期值得跟踪：

```text
Realtime Inference
Stateful Session Placement
Inference Handoff
Low-latency Delegation
Multimodal Streaming
```

---

## 4.2 Agent Governance 会从 RBAC 走向 Stateful Capability Control

Dogwood 和 Cloudflare Agent Access Model 本周独立指向相似问题：

传统：

```text
Who are you?
What resource can you access?
```

Agent：

```text
Who are you?
What task are you doing?
What have you already accessed?
What capabilities remain?
```

Cloudflare 的 AAM 甚至提出 **Trust Ratchet**：触发敏感事件后，只允许能力单向缩减。([Cloudflare Blog][7])

这很可能发展成 Agent Runtime 的标准基础设施。

---

## 4.3 Environment 会成为 Agent Research Stack 的第一等资源

传统 ML 基础设施强调：

```text
Dataset
Model
Training
Serving
```

Agent 系统会多一个同等重要的实体：

```text
Environment
```

因为 Environment 同时决定：

* Tool Availability
* State
* Side Effects
* Reward
* Failure
* Evaluation

Orchard 把这一层独立出来，是一个值得长期追踪的方向。([Microsoft][3])

## 4.4 AI Infra Observability 会继续向 GPU 内部延伸

未来：

```text
OpenTelemetry Trace
```

很可能不能只停在：

```text

→ Model Server
```

而需要继续进入：

```text

→ Batch
→ CUDA
→ Kernel
→ NCCL
```

TELLER 是这个方向的研究信号，而不是成熟标准。([arXiv][4])

AgentCompile 最值得追踪的不是 LLM 写 CUDA，而是：

```text

Deterministic Verification

因此最可能先成功的领域是：

```

因为这些领域通常存在较强的正确性或性能 Oracle。([arXiv][5])

# 5. Noise Filter

### “Realtime AI 就是更快的模型”

暂时降低优先级。GPT‑Live 的生产经验恰恰显示，瓶颈可能首先发生在 CPU Stream Handler、Queue、Network、Geography、Reconnect 和 State Recovery，而不是 GPU Throughput。([OpenAI][1])

### “有 MCP / RBAC 就已经解决 Agent Security”

不成立。传统 Authorization 主要处理当前 Action，无法自然表达 Action Sequence、累计额度、Exposure History 和 Capability Reduction。Dogwood 和 AAM 都在补这一层。([Amazon Web Services, Inc.][2])

### “Benchmark 分数就是 Agent Training 能力”

需要降权。Orchard 最值得关注的是 Environment Reuse 和 Real-harness Training，而不是 69.7% 或 73.0% 本身。Benchmark 仍然受到 Harness、Environment、Retry 和 Evaluation Protocol影响。([Microsoft][3])

### “让 LLM 自己做 Root Cause Analysis”

缺少 Evidence Pipeline 时优先级低。TELLER 的合理部分正是先构建确定性的 Cross-layer Evidence，再让模型做解释，而不是让模型直接猜日志。([arXiv][4])

### “LLM-generated CUDA 会取代 Compiler Engineer”

当前证据不足。AgentCompile 依赖大量 compiler-derived candidate space、Contract、Validation、Benchmark 和 Fallback；可靠性来自工程 Harness，而不是模型自由生成能力。([GitHub][9])

### “AI-native Storage 就意味着必须采购专用硬件”

NVIDIA 本周 Vera Storage Benchmark 展示了加密、压缩、Checksum 和 Recovery 等 CPU-side Storage Data Path 对 AI Workload 的影响，但结果来自厂商自己的硬件测试。更值得保留的是 **Storage Processing 可能重新成为 Agent / KV / Memory Workload 的瓶颈**，而不是具体硬件性能倍率。([NVIDIA Developer][10])

# 6. Engineering Practice Signals

| 本周实践信号                        | 值得吸收的工程动作                                                                                                                         |
| ----------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| GPT‑Live Dedicated Media Path | 将 latency-critical path 与 Tool / Business Logic 隔离                                                                                |
| Stateful Inference Handoff    | Context Compaction 或实例升级使用 warm replacement + cutover                                                                             |
| Production Shadow Traffic     | 对新 Agent/Inference Path 使用 Read-only Shadow Replay                                                                                |
| Session Capacity Planning     | Capacity 指标从 GPU QPS 扩展到 concurrent session + CPU + network                                                                       |
| Dogwood Temporal Policy       | 将 Tool History 作为 Policy Input                                                                                                    |
| Request-based Rate Limit      | 并发副作用约束优先统计 Intent/Request，而非完成 Response                                                                                          |
| Fail-closed Policy Store      | Runtime Verification State 丢失时不要默认放行                                                                                              |
| Orchard Env                   | 将 Sandbox 从 Trainer 中抽成独立 Service                                                                                                 |
| Real-harness Training         | 避免训练 Loop 与生产 Harness 不一致                                                                                                         |
| Environment Versioning        | Eval 记录 Image、Harness、Tool、Policy、Task Snapshot                                                                                   |
| TELLER Cross-layer Trace      | 建立 Request ↔ Batch ↔ CUDA Kernel Correlation                                                                                      |
| Trace Compression             | 将原始 Trace 转为结构化 Evidence，而不是直接交给 LLM                                                                                              |
| AgentCompile Admission        | Generated Artifact 必须经过 correctness + benchmark gate                                                                              |
| Never-worse Fallback          | AI-generated system optimization 保留已知安全实现                                                                                         |
| Stacked PR                    | AI 生成大型 Change 时优先强制逻辑分解，而不是接受巨型 Diff；GitHub 本周也专门提出用 stacked PR 解决 AI-generated large PR 的 Reviewability。([The GitHub Blog][11]) |

## 本周工程结论

如果只保留一个架构判断，我会保留：

> **未来 AI Systems Engineer 最核心的工作，不是让模型获得更多自由，而是设计模型自由发生在哪一层、哪些状态必须显式存在，以及哪一层拥有最终 Authority。**

本周五个信号可以被统一成这样一张图：

```text
                    Probabilistic Intelligence
                              │
                ┌─────────────┴─────────────┐
                │                           │
         Realtime Model               Reasoning / Agent
                │                           │
                ▼                           ▼
          Fast Data Path              Tool / Environment
                                             │
                                             ▼
                                      Runtime Policy
                                             │
                                             ▼
                                   Deterministic Systems
                                   ├── Authorization
                                   ├── Validation
                                   ├── Sandbox
                                   ├── Trace
                                   ├── Compiler
                                   └── Benchmark
```

GPT‑Live 在做 **latency boundary**；Dogwood 在做 **behavior boundary**；Orchard 在做 **environment boundary**；TELLER 在做 **evidence boundary**；AgentCompile 在做 **admission boundary**。([OpenAI][1])

这几个方向比“哪个 Agent Framework 本周又增加了什么 API”更值得长期积累，因为它们对应的是不会随着模型名字更换而消失的系统问题：**实时性、状态、隔离、权限、可观测性、验证与故障恢复。**
