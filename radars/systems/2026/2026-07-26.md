# AI Systems Engineering 技术雷达（高信号版）

**观察窗口：2026 年 7 月 20 日—7 月 26 日**

本期筛选出 5 个高信号变化。核心主题不是模型能力继续上升，而是：

> **Agent 基础设施正在从“模型调用框架”演化为具有协议语义、资源预算、治理决策、执行控制面和效果度量的完整计算系统。**

# 1. Executive Summary

* **MCP 正从有状态连接协议转向无状态、HTTP-native 的工具协议。** 新版本移除协议层 Session 和初始化握手，使请求可以落到任意实例，同时引入可路由 Header、缓存语义、W3C Trace Context、扩展机制和正式 Conformance Suite。GitHub MCP Server 已提前支持该版本。长期看，MCP Server 会越来越接近标准云服务，而不是绑定单一 Agent Session 的长连接进程。([The GitHub Blog][1])
* **Agent 自主性开始被表达为显式资源预算。** Claude Code 本周为 Sub-agent 增加默认并发上限，默认关闭嵌套派生，并加入严格网络 Allowlist、结构化 Runner 故障分类和多层 Sub-agent Trace 转发。生产系统不再依赖“请不要创建太多 Agent”这类 Prompt，而是通过 Runtime Policy 限制并发、深度和网络能力。([GitHub][2])
* **Human-in-the-loop 正从聊天交互转化为结构化治理协议。** GitHub Issues 的 Agent Automation 开始为每次修改附带 Confidence、Rationale 和 Approval 状态，但 GitHub 明确说明 Approval 只是工作流便利，不是安全边界。这表明“Agent 建议什么”和“系统允许什么”必须是两个独立层次。([The GitHub Blog][3])
* **任务控制面正在从 IDE 扩展到 Issue Tracker。** Copilot Cloud Agent 可直接接受 Linear Issue，在临时环境中运行、持续回传进度、创建 Draft PR，并支持运行中追加指令。长期趋势是：任务系统负责意图、状态与人工 Steering，执行环境负责代码和工具运行。([The GitHub Blog][4])
* **Agent 度量正在从活跃用户数转向采用深度与工程产出。** GitHub 新 Dashboard 将用户划分为 Code-first、Agent-first、Multi-agent/Copilot App 等阶段，并展示 PR 合并量和速度。但这些指标仍主要是相关性观测，不能直接证明质量、维护成本或真实生产力提升。([The GitHub Blog][5])

# 2. Top 5 AI Systems Signals

## Signal 1：MCP 无状态化，使 Tool Infrastructure 可以使用普通云原生架构

**Source:** GitHub MCP Server；Model Context Protocol Specification RC
**Date:** 2026-07-23
**Evidence Level:** Official
**Technology Maturity:** Production Adoption（GitHub 已提前支持，正式规范计划于 7 月 28 日发布）

### 1. 发生了什么

新 MCP 规范移除了：

* `initialize` / `initialized` 握手
* `Mcp-Session-Id`
* 协议层 Session

每个请求都包含完成处理所需的协议版本、客户端信息和能力元数据，因此可以由任意 Server Instance 处理。GitHub MCP Server 因此删除了 Redis Session、初始化时的数据库写入和每次调用的数据库读取。([The GitHub Blog][1])

规范同时增加：

* `Mcp-Method` 和 `Mcp-Name` Header，用于路由、限流和观测
* `ttlMs` 与 `cacheScope`，用于 Tool List 和 Resource 缓存
* W3C `traceparent`、`tracestate`、`baggage`
* Extensions Framework
* Tasks 与 MCP Apps 扩展
* OAuth/OIDC 安全加固
* 正式 Conformance Suite([Model Context Protocol Blog][6])

### 2. 工程上改变了什么

旧架构通常要求：

```text
Client
  ↓ sticky routing
MCP Server Instance
  ↓
Shared Session Store
```

新架构可以是：

```text
Client
  ↓
Round-robin Load Balancer
  ↓
Any MCP Server Instance
```

如果应用确实需要状态，应返回显式 Handle，例如 `browser_id`、`task_id` 或 `basket_id`，并要求模型在后续 Tool Call 中传回，而不是把状态隐藏在 Transport Session 中。([Model Context Protocol Blog][6])

### 3. Architecture impact

生产 MCP Platform 需要重新定义四个边界：

1. **Protocol State：** 原则上无状态。
2. **Application State：** 使用显式 Handle 或持久化业务对象。
3. **Execution State：** 由 Task Extension 或外部 Workflow Engine 管理。
4. **Observability State：** 通过 Trace Context 跨 Host、Client、Server 和下游服务关联。

这使 MCP 更容易接入：

* Kubernetes 水平扩容
* API Gateway
* CDN/Cache
* 标准 Rate Limiter
* OpenTelemetry
* Service Mesh

### 4. Alternative approach 和 trade-off

| 方案                      | 优点            | 主要代价                                   |
| ----------------------- | ------------- | -------------------------------------- |
| 协议层 Session             | 应用开发简单，状态自动关联 | Sticky Routing、共享 Session Store、故障恢复复杂 |
| 无状态请求 + 显式 Handle       | 易扩容、易重试、状态可观察 | Handle 生命周期和权限需自行管理                    |
| Durable Workflow Engine | 长任务可靠、支持恢复    | 引入额外基础设施和状态模型                          |
| Agent 自己在 Context 中保存状态 | 实现最简单         | 不可靠、不可审计，Context 压缩后容易丢失               |

### 5. 对 AI Systems Engineer 的启发

设计 Tool Platform 时，应明确回答：

* 状态由谁拥有？
* Handle 能否跨用户、跨任务复用？
* Tool Call 是否幂等？
* Client 重试会不会重复执行副作用？
* Cache 失效如何处理？
* Trace 是否能够关联到业务 Task？
* Server Instance 宕机后任务如何恢复？

协议无状态化不会消除状态问题，只是迫使状态从隐式连接元数据转化为显式系统设计。

## Signal 2：并发数、派生深度和网络出口成为 Agent Runtime 的一等 Policy

**Source:** Anthropic Claude Code v2.1.217、v2.1.219
**Date:** 2026-07-21、2026-07-24
**Evidence Level:** Official
**Technology Maturity:** Production Adoption

### 1. 发生了什么

Claude Code 增加了：

* 默认最多同时运行 20 个 Sub-agent
* 默认禁止 Sub-agent 继续派生嵌套 Sub-agent
* 可配置最大派生深度
* `sandbox.network.strictAllowlist`
* 多层 Sub-agent 输出转发
* Self-hosted Runner 的结构化失败分类
* MCP 配置验证错误在 Headless 初始化事件中暴露([GitHub][2])

同一时期还修复了 MCP Tool Output 截断后仍在内存保留完整结果、工作目录 Symlink 导致 Session 逃离 Workspace、配置路径扩展可能耗尽内存等问题。([GitHub][2])

### 2. 工程上改变了什么

过去，Multi-agent 控制常写在 Prompt 中：

```text
尽量不要创建过多 Sub-agent。
```

现在逐渐变成真正的 Runtime Constraint：

```text
max_concurrency = 20
max_spawn_depth = 1
network_egress = strict_allowlist
memory_budget = bounded
```

这与线程池、连接池、Kubernetes Resource Limit 和队列消费者并发控制属于同一类系统问题。

### 3. Architecture impact

建议将 Agent Autonomy 拆成多个独立预算：

```text
Autonomy Budget
├── Token Budget
├── Wall-clock Budget
├── Tool-call Budget
├── Concurrency Budget
├── Spawn-depth Budget
├── Network Egress Policy
├── Filesystem Scope
└── Human Approval Budget
```

不要只设置一个总 Token 上限。失控 Agent 可能在 Token 尚未耗尽时，就已经创建大量并发任务、占用外部 API 配额或访问过多网络目标。

### 4. Alternative approach 和 trade-off

**Unbounded Agent Tree**

* 优点：高并行度，适合可完全分解的任务。
* 缺点：成本爆炸、任务重复、故障难归因、输出合并困难。

**Bounded Hierarchical Agents**

* 优点：仍保留动态分解能力。
* 缺点：需要调优并发和深度，可能限制复杂任务。

**Deterministic DAG**

* 优点：最容易复现、调试和审计。
* 缺点：适应性低，工作流变化需要人工修改。

### 5. 对 AI Systems Engineer 的启发

生产 Agent Runtime 应具备类似 Admission Control 的机制：

1. 运行前估算资源。
2. 检查组织与任务预算。
3. 限制并发和递归。
4. 记录拒绝或降级原因。
5. 在预算临界点触发压缩、降级模型或人工确认。
6. 对 Runner Crash、Config Error、Hook Error、Model Error 使用不同恢复策略。

“让 Agent 自己决定是否继续扩张”不是可靠的资源管理方案。

## Signal 3：Confidence、Rationale 与 Approval 正在形成 Agent Action Envelope

**Source:** GitHub Issues Agent Automation Controls
**Date:** 2026-07-23
**Evidence Level:** Official
**Technology Maturity:** Production Adoption（Public Preview）

### 1. 发生了什么

GitHub Issues 的 Agent Automation 现在可为 Label、Issue Type、Assignee、Field、Close 等操作附带：

* **Confidence：** High / Medium / Low
* **Rationale：** 为什么执行该动作
* **Approval State：** 自动执行或等待人工接受

管理员可以设置置信度阈值：高置信度动作自动应用，中低置信度动作进入待审面板。([The GitHub Blog][3])

GitHub 同时明确说明，这些 Approval 是工作流便利，而不是服务器端安全控制；如果 Agent 已拥有直接修改 Issue 的权限，它仍然可以绕过 Suggestion Flow 直接执行。([The GitHub Blog][3])

### 2. 工程上改变了什么

Agent Action 不应只是：

```json
{
  "tool": "close_issue",
  "issue_id": 123
}
```

更成熟的 Action Proposal 应类似：

```json
{
  "action": "close_issue",
  "target": 123,
  "rationale": "duplicate of #98",
  "confidence": 0.82,
  "evidence": ["semantic_match", "same_stack_trace"],
  "risk_class": "medium",
  "requested_mode": "suggest"
}
```

随后由独立 Policy Engine 决定：

```text
Allow / Deny / Require Approval / Reduce Scope
```

### 3. Architecture impact

应严格区分三层：

| 层次                  | 负责内容          |
| ------------------- | ------------- |
| Agent Reasoning     | 提出动作、理由和置信度   |
| Workflow Governance | 决定是否需要人工审查    |
| Authorization       | 判断调用者是否拥有执行权限 |

Agent 的 Confidence 不能替代 IAM；Human Approval 也不能替代服务器端权限检查。

### 4. Alternative approach 和 trade-off

* **全部自动执行：** 吞吐量最高，但错误影响半径大。
* **全部人工审批：** 风险低，但人类容易成为瓶颈。
* **基于置信度审批：** 可减少审查量，但依赖置信度校准。
* **基于风险等级审批：** 对高风险动作更有效，但需要明确业务分类。
* **Confidence × Risk 联合策略：** 最合理，但 Policy 设计和维护成本更高。

### 5. 对 AI Systems Engineer 的启发

应测试的不是模型是否“自信”，而是：

* 置信度是否经过校准？
* 80% Confidence 是否真的约等于 80% 正确率？
* 不同操作类型是否应使用不同阈值？
* 哪些动作即使高置信度也必须审批？
* Rationale 是否与真实 Tool Evidence 对应？
* 人类拒绝后的反馈是否进入后续 Evaluation？

这会逐渐成为 Agent Governance 的标准数据模型。

## Signal 4：Issue Tracker 正成为 Agent Control Plane，执行环境成为可替换 Worker

**Source:** GitHub Copilot Cloud Agent for Linear
**Date:** 2026-07-23
**Evidence Level:** Official
**Technology Maturity:** Production Adoption（Generally Available）

### 1. 发生了什么

Linear Issue 可以直接分配给 Copilot Cloud Agent。Agent 会：

* 分析 Issue
* 在 GitHub Actions 驱动的临时环境中工作
* 创建 Draft PR
* 将进度持续写回 Linear Timeline
* 完成后请求人工 Review

用户可以按 Issue 或 Workspace 配置模型、Custom Agent、Base Branch、Working Branch，并通过评论在运行过程中追加指令。([The GitHub Blog][4])

### 2. 工程上改变了什么

Agent 入口不再必须是 IDE：

```text
Linear / GitHub Issue
        ↓
Task Control Plane
        ↓
Cloud Agent Session
        ↓
Ephemeral Runner
        ↓
Branch / Commit / Draft PR
```

Work Item 保存：

* 用户意图
* 讨论历史
* 业务优先级
* Agent 运行状态

Git 与 CI 保存：

* 实际变更
* 验证结果
* 可审查 Artifact

### 3. Architecture impact

这要求系统具有稳定的跨产品身份关联：

```text
Issue ID
↕
Agent Session ID
↕
Runner ID
↕
Branch / Commit / PR
↕
CI Run
↕
Deployment / Incident
```

如果这些 ID 不能贯通，用户只能看到“Agent 已完成”，却无法解释它执行了哪些操作、消耗多少资源，以及最终 Artifact 是否真正由该任务产生。

### 4. Alternative approach 和 trade-off

| 模式                     | 优点              | 缺点                  |
| ---------------------- | --------------- | ------------------- |
| IDE Local Agent        | 上下文丰富、延迟低       | 依赖开发者设备，难持续运行       |
| Cloud Background Agent | Durable、可审计、可并行 | 环境准备、Secrets 和成本更复杂 |
| CI Agent               | 可重复、接近交付流程      | 用户 Steering 较慢      |
| Issue-driven Agent     | 意图和团队状态清晰       | Issue 描述质量直接影响执行效果  |

### 5. 对 AI Systems Engineer 的启发

建设后台 Agent 时，应优先设计：

* Task Lifecycle
* Session Resume
* Progress Event Schema
* Steering Protocol
* Artifact Correlation
* Ephemeral Environment Provisioning
* Secret Injection
* Human Takeover
* Cancel 与 Retry 语义

真正的产品单位越来越可能是 **Durable Task**，而不是某一次聊天 Session。

## Signal 5：Agent Evaluation 开始从“是否使用”转向采用阶段和工程产出

**Source:** GitHub Copilot Usage Metrics Impact Dashboard
**Date:** 2026-07-22
**Evidence Level:** Official
**Technology Maturity:** Production Adoption

### 1. 发生了什么

GitHub 新 Dashboard 将用户划分为：

* Passive
* Phase 1：Code-first
* Phase 2：Agent-first
* Phase 3：Multi-agent 或 Copilot App

并展示：

* 每用户每月平均合并 PR 数
* PR 合并速度中位数
* 每个阶段的用户数量
* 每日代码行数
* 六个月的采用与吞吐趋势([The GitHub Blog][5])

### 2. 工程上改变了什么

企业开始构建以下映射：

```text
AI Usage Pattern
        ↓
Adoption Cohort
        ↓
Engineering Activity
        ↓
Delivery Outcome
```

这比仅统计 Seat、活跃用户或 Prompt 数量更接近实际价值，但仍不足以证明因果关系。

### 3. Architecture impact

Agent Analytics Platform 至少需要连接：

* IDE / CLI / Cloud Agent Trace
* GitHub PR 和 Commit
* CI/CD
* Issue Tracker
* Incident Management
* 成本系统
* 组织与团队信息

建议使用统一 `agent_run_id` 或 Correlation Metadata，将一次 Agent Run 与后续 Artifact 和生产结果关联。

### 4. Alternative approach 和 trade-off

**活动指标**

* Prompt、Session、Token
* 易采集
* 不能说明价值

**产出指标**

* PR、代码行数、完成 Issue
* 更接近工作结果
* 容易被数量驱动误导

**质量指标**

* Rework、Escaped Defect、Rollback
* 更可信
* 需要长期数据

**因果评估**

* A/B、Matched Cohort、Difference-in-Differences
* 最具解释力
* 实施成本高且容易受组织行为影响

### 5. 对 AI Systems Engineer 的启发

建议把 Evaluation 分成三层：

| 层次       | 典型指标                                  |
| -------- | ------------------------------------- |
| Runtime  | Token、Latency、Retry、Tool Error        |
| Artifact | Patch、PR、Test、Review Finding          |
| Outcome  | Lead Time、Rework、Defect、Incident、业务结果 |

只有三个层次联合起来，才能判断 Agent 是真正改善系统，还是仅生成了更多活动。

## Why This One

MCP 无状态化不是局部 API 调整，而是改变了：

* Server 如何横向扩展
* 状态放在哪里
* 长任务如何建模
* Gateway 如何路由和检查请求
* Tool List 如何缓存
* Trace 如何跨服务传播
* Client 与 Server 如何做兼容性验证
* OAuth/OIDC 如何接入

它直接连接 Agent Tool Use、Cloud Infrastructure、Distributed Tracing、Security 和 Durable Workflow，是本周对 AI Systems Engineer 最具长期价值的变化。([Model Context Protocol Blog][6])

## Practical Experiment：将一个 Session-based MCP Server 改造成 Stateless Server

**预计时间：2—3 小时**

### 目标

验证无状态 MCP Server 是否可以：

* 在两个实例之间随机负载均衡
* 不依赖共享 Session Store
* 保持业务状态正确
* 保持 Trace 连续
* 通过 Draft Conformance Test

### 步骤

1. 构建一个简单的 MCP Server，提供：

   * `create_workspace`
   * `add_file`
   * `get_workspace`
2. 旧版本把 Workspace ID 存入协议 Session。
3. 新版本由 `create_workspace` 返回显式 `workspace_id`。
4. 后续 Tool Call 必须传入 `workspace_id`。
5. 启动两个 Server Instance，使用 Round-robin Proxy，不启用 Sticky Session。
6. 添加：

   * `Mcp-Method`
   * `Mcp-Name`
   * `traceparent`
   * Tool List 的 TTL
7. 使用 MCP Conformance Suite 分别运行旧版和 Draft Spec 测试。
8. 注入：

   * Instance Restart
   * Duplicate Request
   * Timeout + Retry
   * Invalid Handle
   * Expired Handle

### 验证方式

通过标准：

* 请求可在不同 Instance 之间切换。
* 不发生 Workspace 状态串线。
* 重试不会重复执行副作用。
* Trace 能跨 Client、MCP Server 和 Storage 关联。
* Conformance Core 和 Draft Suite 通过。
* 不需要 Redis 或 Sticky Load Balancer。

# 4. Research Direction

## 4.1 Stateless Protocol，Explicit Application State

越来越多 Agent 基础设施会采用：

```text
Stateless Transport
+
Explicit Resource Handles
+
Durable Workflow State
```

这比将所有历史塞入 Agent Context 更可扩展，也更容易测试和审计。MCP 的变化是这一方向的重要标准化信号。([Model Context Protocol Blog][6])

## 4.2 Bounded Autonomy 将成为 Runtime 标配

Concurrency、Spawn Depth、Tool Budget、Egress、Filesystem Scope 和 Duration 会像 CPU、Memory 和 Network Quota 一样被显式配置。Claude Code 本周的默认并发限制与嵌套策略表明，无边界派生正在从“能力”转化为需要治理的风险。([GitHub][2])

## 4.3 Agent Intent 将成为标准中间表示

未来 Agent Tool Call 可能不只包含参数，而会携带：

* Intent
* Evidence
* Rationale
* Confidence
* Risk
* Approval Requirement

这使 Runtime、Policy Engine 和人类 Reviewer 能够使用统一对象协作。GitHub Issues 的实现是这一方向的早期生产信号。([The GitHub Blog][3])

## 4.4 Control Plane 与 Execution Plane 进一步分离

Issue Tracker、IDE 和移动端负责：

* Task Intake
* Steering
* Approval
* Progress

Cloud Runner、Sandbox、CI 和 Browser Runtime 负责：

* Execution
* Isolation
* Artifact Creation

Linear 与 Copilot Cloud Agent 的整合说明这种分离已进入普通工程工作流。([The GitHub Blog][4])

## 4.5 Agent Evaluation 将走向因果与质量度量

采用阶段、PR 数和合并速度只是第一步。长期需要将 Agent 使用与：

* 缺陷
* 返工
* Incident
* Review 负担
* 维护成本
* 业务 Outcome

进行关联，并逐步使用更严格的实验与准实验方法。([The GitHub Blog][5])

# 5. Noise Filter

## “MCP 无状态意味着应用不再需要状态”

错误。协议不再维护 Session，但 Browser、Task、Workspace 和 Transaction 仍然需要状态。区别是这些状态必须成为显式业务对象，而不是隐藏在连接层。([Model Context Protocol Blog][6])

## “Human Approval 就是安全控制”

GitHub 明确说明其 Approval 不是 Server-side Security Boundary。Agent 权限仍必须由 IAM、Policy Engine 和 Tool Server 强制执行。([The GitHub Blog][3])

## “更多 Sub-agent 会自动提高质量”

Anthropic 默认限制并发并关闭深层嵌套，本身说明无界 Agent Tree 会产生资源、可观测性和可靠性问题。多 Agent 只有在任务可分解、职责独立且结果可验证时才有价值。([GitHub][2])

## “PR 数增加就代表生产力提升”

PR、代码行数和 Merge Velocity 只能描述活动和吞吐。它们不能单独说明质量、返工、长期维护负担和业务价值。GitHub Dashboard 应被当作诊断入口，而不是最终 KPI。([The GitHub Blog][5])

## “协议兼容等于生产可靠”

通过 MCP Schema 或 Handshake 不代表：

* Tool 行为正确
* 权限合理
* 重试安全
* 状态隔离
* Server 可恢复

协议 Conformance 与业务级 Evaluation 必须同时存在。([GitHub][7])

# 6. Engineering Practice Signals

| 本周信号                              | 建议工程动作                                             |
| --------------------------------- | -------------------------------------------------- |
| MCP 无状态化                          | 将隐式 Session State 改为显式 Handle                      |
| MCP Conformance Suite             | 在 Client/Server CI 中固定运行 Core、Auth 和 Draft Suite   |
| Sub-agent 并发与深度限制                 | 为 Agent Runtime 增加 Admission Control 和资源预算         |
| Strict Network Allowlist          | 默认拒绝未知 Egress，按任务声明网络 Capability                   |
| Structured Runner Failures        | 区分 Config、Hook、Runner、Model、Tool 和 Policy Failure  |
| Confidence / Rationale / Approval | 定义标准 Action Proposal Schema                        |
| Approval 不是安全边界                   | 将 Authorization 保留在服务器端 Policy Enforcement         |
| Linear 驱动 Cloud Agent             | 建立 Issue→Session→Runner→Branch→PR 的 Correlation ID |
| Impact Dashboard                  | 同时采集 Runtime、Artifact 和 Outcome 指标                 |
| Stateless MCP Trace Context       | 使用 W3C Trace Context 连接 Host、Client、Server 和下游服务   |

## 本周工程结论

本周最值得长期保留的判断是：

> **Agent 系统正在从“LLM 加工具”转化为一种受治理的分布式执行系统。**

其核心构件逐渐明确为：

```text
Stateless Protocol
+ Explicit State
+ Bounded Autonomy
+ Action Intent
+ Policy Enforcement
+ Durable Task
+ Conformance Testing
+ Outcome Evaluation
```

未来 AI Systems Engineer 的核心优势，不是掌握更多 Agent Framework API，而是能够为这些构件定义清晰语义、故障边界、资源预算和验证方法。
