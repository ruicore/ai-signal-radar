## Signal 2：Agent Runtime 的核心问题转向 Session、并发与重试一致性

**Source:** OpenAI Agents SDK Python v0.18.3
**Date:** 2026-07-17
**Evidence Level:** Official / Reproducible Engineering Practice
**Technology Maturity:** Open Source Experiment

### 1. 发生了什么

v0.18.3 包含一组高度生产化的修复：

* 可配置 Task Span 和 Turn Span
* Realtime Session 中记录 Response Usage
* 序列化 Conversation Session 初始化
* 并发 Run 之间隔离 Computer Provider
* 模型重试时保留已流式传入的 Session Input
* 防止复用过期的 Prepared-item Identity
* 修复 SQLite Session 元数据泄漏
* 限制严格 JSON Schema 转换中的 `$ref` 展开
* 对非工具 Trace Error 进行脱敏

### 2. 工程上改变了什么

这些修复共同说明，Agent Runtime 不只是：

```text
LLM → Tool → LLM
```

而是一个包含以下语义的异步执行系统：

```text
Session State
+ Concurrent Runs
+ Streaming
+ Retry
+ Identity
+ Durable Storage
+ Resource Bounds
+ Telemetry
```

### 3. Architecture impact

生产 Agent Runtime 应显式定义以下不变量：

* 一个 Run 的 Provider、Context 和 Tool State 不得泄漏到另一个 Run。
* Retry 不得丢失或重复用户输入。
* Session 初始化必须具有并发安全性。
* Item Identity 不能依赖可能被回收或复用的进程内对象身份。
* Schema 解析必须有深度、大小或时间限制。
* Trace 必须区分可诊断信息和敏感信息。

### 4. Alternative approach 与 trade-off

**直接调用模型 API** 能减少框架状态，但 Session、Retry、Tracing 和 Tool Lifecycle 都需要自行实现。

**使用完整 Agent SDK** 能获得统一抽象，但也引入更多隐式状态和复杂生命周期。采用前不应只验证 Happy Path，而应测试框架在取消、超时、重试和并发下的语义。

### 5. 对 AI Systems Engineer 的启发

Agent Framework 选型时，不应只比较：

* 支持多少模型
* 是否支持 Multi-agent
* 有多少 Tool Integration

更重要的是查看：

* 并发测试
* 故障注入测试
* Session 原子性
* Retry 语义
* Cancel/Timeout 清理
* Trace 数据治理

## Signal 3：MCP Tool Identity 成为新的供应链边界

**Source:** GitHub Copilot in Visual Studio — June Update
**Date:** 2026-07-14
**Evidence Level:** Official
**Technology Maturity:** Production Adoption

### 1. 发生了什么

Visual Studio 现在会在启动 MCP Server 时，将其配置和资产指纹与已信任基线比较。检测到变化后，用户必须重新检查并批准，工具才能运行；该能力默认开启。

### 2. 工程上改变了什么

MCP Server 不应只用名称和 URL 标识。更完整的 Tool Identity 至少应包含：

```text
Server source
Configuration hash
Executable / image digest
Tool schema hash
Requested scopes
Network destinations
Authentication identity
```

### 3. Architecture impact

推荐把 Tool Registry 从简单目录升级为受治理的供应链组件：

```text
Registry Entry
   ↓
Verified Artifact / Configuration
   ↓
Capability and Scope Review
   ↓
Runtime Sandbox
   ↓
Invocation Audit
```

工具升级应类似依赖升级或容器镜像发布，而不是无感替换。

### 4. Alternative approach 与 trade-off

* **Trust on First Use：** 实现简单，但首次安装若已被污染，基线本身不可信。
* **签名 Artifact：** 信任更强，但需要签名、发布和密钥基础设施。
* **固定 Hash Allowlist：** 控制严格，但升级运维成本高。
* **每次弹窗确认：** 易实现，但可能造成 Approval Fatigue。

### 5. 对 AI Systems Engineer 的启发

MCP 统一了协议，并没有消除以下问题：

* 谁发布了工具
* 当前运行的是否是审核版本
* Tool Schema 是否发生变化
* 权限是否扩大
* 凭据会流向哪里

未来 Tool Governance 很可能成为 Agent Platform 的标准基础设施。

## Practical Experiment：Agent Runtime Invariant Test

**预计时间：2—3 小时**

### 目标

验证并发执行和流式重试过程中是否存在：

* 跨 Run 状态泄漏
* 输入丢失或重复
* Provider 复用错误
* Trace Correlation 错位

### 步骤

1. 分别创建安装 v0.18.2 和 v0.18.3 的两个 Python 环境。
2. 实现一个 Fake Model Provider：

   * 接收唯一 `run_id`
   * 输出两段 Stream Event
   * 第一次调用在第一段后主动抛出可重试异常
3. 并发启动 30—50 个 Run，每个 Run 使用不同输入标记。
4. 记录：

   * Provider Instance ID
   * Run ID
   * 输入事件序列
   * Retry 次数
   * 最终 Session Items
   * Trace ID
5. 对两个版本运行相同测试。
6. 增加一个递归或高度复用 `$ref` 的 Tool Schema，记录转换时间与峰值内存。

### 验证方式

通过条件：

* 每个 Run 只出现自己的输入标记。
* Retry 后输入不丢失、不重复。
* Trace 与 Session 的 Run ID 一致。
* 并发量增加时不存在共享 Provider 状态污染。
* Schema 转换能够在明确资源边界内结束。

不必强求复现每个历史 Bug；实验的价值在于建立可持续执行的 Runtime Invariant Suite。

# 5. Noise Filter

## “支持 BYOK 就实现了模型可移植性”

BYOK 解决认证和路由，不解决：

* Tool Calling 行为差异
* Context 管理差异
* Prompt 遵循差异
* Retry 和错误语义
* 安全策略差异

因此应降低对“零成本切换模型”宣传的信任。

## “MCP 标准化后工具就是可信的”

协议兼容与供应链可信是两个问题。工具仍可能发生代码、配置、Schema 和权限变化；本周新增的指纹验证本身说明 Runtime 必须独立处理信任。

## “更多 Agent 指标意味着生产力已经可衡量”

Session、Token、PR 和 Comment 数量只能描述活动。若没有缺陷、返工、交付周期和维护成本，它们无法回答 Agent 是否真正改善工程结果。

## “长 Context 可以掩盖 Runtime 状态问题”

Session 竞态、Retry 丢失、跨 Run 污染和错误身份复用不会因为 Context 更长而消失。这些属于执行语义问题，而不是模型容量问题。

## “Repository Instructions 越多，Agent 治理越成熟”

文件数量不是成熟度。真正应衡量的是：

* 指令是否存在冲突
* 优先级是否明确
* 行为是否经过 Evaluation
* 是否能安全回滚
* 是否有不可被仓库覆盖的组织策略
