# AI Systems Engineering 技术雷达（高信号版）

**观察窗口：2026 年 8 月 17 日—8 月 23 日**

本期完全按照当前 7 天窗口重新检索与验证，不沿用此前周报中的案例或结论。最终保留 **5 个高信号变化**。相比模型发布本身，这一周更值得关注的是几个系统边界正在变得清晰：**Agent Harness 正在成为独立 Runtime；概率式 Agent 开始被限制在 Build Plane；企业开始集中治理 Endpoint Agent；电力进入 AI Scheduler 的资源模型；Evaluation 则开始从即时 Judge 走向可审计、时间隔离的真实结果。**

# 1. Executive Summary

* **本周最重要的结构性变化，是 Harness 正从“Agent Framework 的内部代码”变成独立系统边界。** OpenAI 8 月 19 日明确把 Codex 的可复用核心定义为 Agent Harness：负责 Context、Tool、Sandbox、Approval、Progress、Failure 和跨 Turn State；Microsoft 8 月 18 日发布的 Agent Lightning v1.0 更进一步，让生产时实际使用的 Harness 直接参与 RL 训练，而不是重新在 Trainer 内实现一份简化 Agent Loop。两条独立信号共同说明：未来评估一个 Agent 时，`Model` 已经不足以作为版本单位，至少应该是 `Model × Harness × Tool Contract × Environment`。([BERJAYA][1])
* **Agent 的一个重要生产模式正在形成：Agents in Dev，Deterministic Artifacts in Prod。** AWS 本周发布的 ADOP Reference Architecture 让 Agent 在开发期生成 ETL、Data Quality、Semantic Definition、IAM/Cedar Policy 等 Artifact，经人工和 CI/CD 验证后，生产环境只运行确定性的 PySpark、SQL、Airflow DAG 和 Policy，而默认不依赖模型 Runtime。这种模式可以理解为把 LLM 当作一种“概率式编译器”，而不是永久在线的业务依赖。([Amazon Web Services, Inc.][2])
* **企业 Agent Governance 正在从云端 API 下沉到开发者 Endpoint。** GitHub Copilot for JetBrains 本周支持企业统一配置 Plugin Source、MCP Allow/Deny List、OpenTelemetry Collector 与 Content Capture Policy，并禁止 Bypass Approvals / Autopilot 等权限模式。长期趋势很可能是：本地 IDE、CLI、Desktop Agent 可以执行，但 Capability、Telemetry 与 Approval Policy 必须由中心 Control Plane 统一下发。([The GitHub Blog][3])
* **AI Infrastructure 的 Scheduler 正在开始理解“电力”这种过去属于 Facilities Team 的资源。** NVIDIA DSX MaxLPS 的 Dynamic Power Software 根据 GPU、Rack、Resource Group 的实时功耗，在固定站点功率预算内动态重新分配 Headroom，并通过 IT/OT Event Bus 接入电网、冷却与 Compute Scheduler。具体性能数字来自 NVIDIA 自身测试，应谨慎看待；但“Power Budget 成为 Scheduler Resource”这一架构变化具有长期意义。([NVIDIA Developer][4])
* **Evaluation 正在从“让另一个模型打分”向 Temporal / Outcome-grounded Evaluation 演化。** 本周一篇关于 Scientific Question Discovery 的论文提出 Historical Backtesting：只允许系统看到某个历史时间点以前的数据，冻结输出，再用未来真实文献判断问题后来是否被回答、证伪或独立提出。论文还发现模型之间高度一致并不代表 Judge 有效：五个 Judge Model 之间的一致性明显高于它们与专业标注者的一致性。这对任何长周期 Agent Eval 都是重要提醒。([arXiv][5])

如果只保留一个本周判断：

> **AI Systems 正在把“概率能力”包进越来越明确的确定性边界中：Harness 决定执行语义，Build Plane 控制生成，Policy Plane 控制权限，Infrastructure Plane 控制资源，而 Evaluation Plane 负责证明结果。**

# 2. Top 5 AI Systems Signals

## Signal 1：Agent Harness 正成为独立 Runtime，同时开始进入训练闭环

**Source:** OpenAI — *Codex as a platform: build on the open agent harness*；Microsoft 等 — *Agent Lightning v1.0: Towards Harnessed Agentic RL*
**Date:** 2026-08-19 / 2026-08-18
**Evidence Level:** **Reproducible Engineering Practice**
**Technology Maturity:** **Industry Pattern**

### 1. 发生了什么

OpenAI 本周将 Codex 的核心抽象明确描述为 **Agent Harness**。App、CLI 与 IDE Extension 背后运行的是同一个执行系统，它负责维护 Context、调用 Tool、执行 Sandbox / Approval Policy、处理失败、Stream Progress，并把任务跨 Turn 持续下去。Codex `app-server` 则通过协议暴露 Thread、Turn、Event 和 Approval 等能力，让其他应用可以嵌入这套 Agent Loop。([BERJAYA][1])

与此同时，Agent Lightning v1.0 提出了 **Harnessed Agentic RL**：不是让训练框架自己实现 Agent–Environment Loop，而是让真正部署时使用的 Harness 保持所有 Context Construction、Tool Execution 和 Control Flow，Trainer 只通过一个 LLM Endpoint Proxy 观察 Harness 发出的模型 Request / Response。论文认为，这可以减少 Training Harness 与 Deployment Harness 之间的语义偏差。([arXiv][6])

这两条信息来自完全不同的方向——一个是应用 Runtime，一个是 RL Training——却指向同一个抽象：

```text
Application / Product
        │
        ▼
     Harness
 ┌───────────────┐
 │ Context       │
 │ Tools         │
 │ Policies      │
 │ State         │
 │ Approvals     │
 │ Recovery      │
 │ Orchestration │
 └───────┬───────┘
         │ LLM API
         ▼
       Model
```

模型并不是完整 Agent，Harness 也不再只是 Framework Glue。

### 2. 工程上改变了什么

传统 Agentic RL 常把 Rollout 理解为一个连续 Token Sequence：

```text
prompt
→ action
→ observation
→ action
→ observation
...
```

但现实 Harness 会：

* 重建 Prompt；
* Context Compaction；
* Spawn Sub-agent；
* Handoff；
* 重新序列化 Tool Result；
* 修改 Chat Template；
* 根据运行状态决定下一次 Model Call。

因此，在 Harnessed Agentic RL 中，一个业务 Rollout 实际上可能对应：

```text
Rollout R
├── Model Call 1 → Sample A
├── Model Call 2 → Sample B
├── Context summary
├── Sub-agent Call → Sample C
└── Model Call 3 → Sample D
```

论文报告，其 Coding Agent 实验中只有约 36% Rollout 最终仍然对应单一 Training Sample，平均每个 Rollout 产生约 2.4 个 Sample。([arXiv][6])

这马上产生几个非常“系统工程”的问题：

* Reward 到底属于 Rollout 还是每个 Sample？
* 一个产生 4 个 Sample 的 Rollout 是否应该比只产生 1 个 Sample 的 Rollout获得 4 倍 Gradient Weight？
* Context 重新 Tokenize 后，旧 Response Token 是否还可以与新 Prompt 安全拼接？
* Sub-agent 导致 Branch 后，怎样保留统计来源？
* 一部分 Sample 用旧 Policy、一部分用新 Policy 是否会产生 Within-rollout Policy Skew？

论文认为 Rollout-level Advantage 和 Rollout-level Loss Normalization 更合理，因为 Harness 的内部切分方式不应改变一个 Task 在训练中的统计权重。([arXiv][6])

### 3. Architecture impact

Agent 未来很可能需要一个正式版本向量：

```text
Agent Version
=
Model Version
+ Harness Version
+ Prompt / Context Policy
+ Tool Schema Version
+ Sandbox Policy
+ Environment Version
```

这会直接影响：

* Evaluation Reproducibility；
* RL Training；
* Production Rollback；
* Incident Investigation；
* A/B Testing；
* Agent Artifact Provenance。

Agent Lightning 的 Control Plane 也很值得注意：API Gateway 保存 Rollout Lifecycle 与 Append-only Event；Rollout Controller 把任务调度成 Kubernetes Job 或 Local Process；Trainer 从 Gateway 读取完成事件并构造训练样本。控制操作要求 Idempotent，`rollout_id` 贯穿 Model Request、Reward、Custom Event 和 Execution Log。([arXiv][6])

这已经非常接近一个传统 Durable Job System，而不是单纯 ML Training Loop。

### 4. Alternative approach 和 trade-off

| 方式                               | 优点                     | 主要问题                                    |
| -------------------------------- | ---------------------- | --------------------------------------- |
| Trainer 内重新实现 Agent Loop         | Training Control 最简单   | 与真实 Harness 行为漂移                        |
| 每个产品自建 Harness                   | 可高度定制                  | 重复实现 State、Approval、Retry、Tracing       |
| Shared Agent Harness             | Execution Semantics 统一 | Harness 逐渐变成复杂平台依赖                      |
| Harness + LLM Proxy Training     | Train / Deploy 行为一致    | Rollout 不再等于单 Training Sequence，统计与调度复杂 |
| End-to-end Black-box Fine-tuning | Integration 最简单        | 难理解 Tool / Context / Failure 行为为何变化     |

值得特别注意的是，OpenAI 在 Codex 文章中引用 ARC-AGI-3 内部结果，声称 Harness 的 Retained Reasoning 与 Context Compaction 可使 GPT‑5.6 Sol 得分从 13.3% 提升至 38.3%，同时降低输出 Token；这是官方结果，不应直接外推到其他任务，但足以说明 **Harness Change 本身可能像 Model Change 一样显著影响 Agent Behavior**。([BERJAYA][1])

### 5. 对 AI Systems Engineer 的启发

以后做 Agent Evaluation，不建议只记录：

```text
model = xxx
temperature = ...
```

至少增加：

```text
model_version
harness_version
context_policy_version
tool_schema_version
sandbox_policy_version
environment_image
rollout_id
```

更进一步，应把 Harness 看成一种 **Agent ABI**：

> 模型看到什么、能调用什么、调用失败后得到什么反馈、什么时候需要审批、Context 如何变化，全部属于 Runtime Contract。

这是一个我认为会长期存在的专业方向：**Harness Engineering**。

## Signal 2：Agents in Dev, Deterministic Artifacts in Prod——Agent 作为概率式 Build System

**Source:** AWS — *Agentic Data Operations Platform (ADOP): Data engineering into hours*
**Date:** 2026-08-21
**Evidence Level:** **Official**
**Technology Maturity:** **Open Source Experiment**

### 1. 发生了什么

AWS 本周发布 ADOP Reference Architecture。它使用 Agent 在开发阶段生成：

* ETL；
* Data Quality Check；
* Semantic Layer Definition；
* Governance Control；
* IAM / Cedar Policy；
* Airflow DAG。

但其默认生产架构明确采用：

> **Agents in dev, artifacts in prod.**

生成结果由工程师 Review，再经过 CI/CD 推入生产；Prod 最终执行的是确定性的 PySpark、SQL、Airflow DAG 与 Policy，而不是每次 Pipeline Run 都再调用一个模型。([Amazon Web Services, Inc.][2])

AWS 甚至明确表示：

> 模型填充 Blueprint，而不是由模型决定 Architecture。

([Amazon Web Services, Inc.][2])

### 2. 工程上改变了什么

这是一个非常有价值的架构模式：

```text
        Build Plane
            │
       LLM / Agent
            │
            ▼
    Candidate Artifacts
            │
      Review / Validate
            │
            ▼
         CI/CD
            │
            ▼
       Runtime Plane
   ┌─────────────────┐
   │ SQL             │
   │ PySpark         │
   │ Airflow DAG     │
   │ IAM / Policy    │
   └─────────────────┘
       no LLM needed
```

换句话说：

> **把概率性放在可回滚的 Build Phase，把生产执行继续保持 Deterministic。**

这与编译器很像：

```text
High-level intent
→ probabilistic compilation
→ static artifact
→ deterministic execution
```

### 3. Architecture impact

这个模式特别适合：

* Data Pipeline；
* Infrastructure-as-Code；
* Policy Generation；
* CI Workflow；
* Migration Script；
* Schema Mapping；
* Query / Dashboard Definition；
* Static Configuration。

这些领域有两个共同特点：

1. 最终 Artifact 可以被静态检查或执行验证；
2. 运行时并不需要持续的开放式语义判断。

因此没有必要为了“AI-native”而把模型永久放进 Critical Path。

ADOP 同时记录每次 Agent Decision 的 Intent、Tool、Outcome 和 Cost，并支持将 Trace 输出到 CloudWatch 或 OpenTelemetry；本地开发是默认模式，需要规模时才迁移到 AgentCore Runtime。([Amazon Web Services, Inc.][2])

### 4. Alternative approach 和 trade-off

| 方案                                    | 优点             | 缺点                                 |
| ------------------------------------- | -------------- | ---------------------------------- |
| Runtime Agent                         | 动态适应性最高        | Non-determinism、Latency、Cost、Audit |
| Agent Build → Static Artifact         | Prod 简单、稳定、可审计 | 无法实时适配未知情况                         |
| Template Generator                    | 最稳定            | 灵活性低                               |
| Human-written Artifact                | 控制最强           | 开发成本高                              |
| Agent Proposal + Human Review         | 风险较低           | Review 可能成为瓶颈                      |
| Agent Proposal + Automated Validation | 高吞吐            | 必须存在可靠 Oracle                      |

### 5. 对 AI Systems Engineer 的启发

判断一个 Agent 是否应该存在于 Production Runtime，可以先问：

> **它是在运行时处理不可预见的语义问题，还是仅仅把 Intent 编译成一个可以事先验证的 Artifact？**

如果是后者，我更推荐：

```text
Agent
→ Generate
→ Validate
→ Freeze
→ Deploy
```

而不是：

```text
Every production execution
→ Ask model again
```

这会显著降低：

* Runtime Failure Surface；
* Token Cost；
* Model Availability Dependency；
* Security Surface；
* Audit Complexity。

需要强调的是，ADOP 目前是 AWS Reference Architecture，博客中“从 weeks 到 hours”之类效率描述主要来自设计目标和方向性观察，而不是公开、独立的大规模 Benchmark，因此本期只把**架构模式**视为强信号，不把效率数字当作已验证事实。([Amazon Web Services, Inc.][7])

## Signal 3：Agent Governance 正在下沉到 IDE / Endpoint Control Plane

**Source:** GitHub — *Enterprise managed settings in GitHub Copilot for JetBrains*
**Date:** 2026-08-18
**Evidence Level:** **Official**
**Technology Maturity:** **Production Adoption**

### 1. 发生了什么

GitHub Copilot for JetBrains 本周增加企业集中 Managed Settings，包括：

* `enabledPlugins`；
* `extraKnownMarketplaces`；
* `strictKnownMarketplaces`；
* `allowedMcpServers`；
* `deniedMcpServers`；
* OpenTelemetry Endpoint / Protocol / Service Name / Resource Attributes；
* Content Capture Policy；
* 禁止 Bypass Approvals / Autopilot。

企业策略优先于本地开发者配置。([The GitHub Blog][3])

这看起来像普通企业管理功能，但从 AI Systems Architecture 看，它是一个很强的信号：

> **Agent Runtime 开始拥有类似 Endpoint Security / Device Management 的 Policy Plane。**

### 2. 工程上改变了什么

本地 Coding Agent 过去经常是：

```text
Developer
   │
   ▼
IDE Agent
├── arbitrary MCP
├── arbitrary plugin
├── local shell
└── local config
```

企业模型正在变成：

```text
               Enterprise Control Plane
                │       │       │
        Plugin Policy  MCP   Telemetry
                │       │       │
                └───┬───┴───────┘
                    ▼
             Endpoint Agent Runtime
                    │
          ┌─────────┼─────────┐
          ▼         ▼         ▼
        IDE       Shell      MCP
```

开发者仍然拥有 Local Execution，但 Capability Envelope 不再完全由本地用户决定。

### 3. Architecture impact

未来企业 Agent Platform 至少需要管理：

```text
Identity
+ Device
+ Agent Client
+ Plugin
+ MCP Server
+ Tool Capability
+ Approval Mode
+ Telemetry Policy
+ Data Capture Policy
```

特别值得注意的是 **OpenTelemetry Content Capture Policy**。

Agent Trace 可能包含：

* Prompt；
* Source Code；
* Database Result；
* Tool Argument；
* Secret；
* PII；
* Generated Patch。

所以“打开 OTel”绝不是简单 Observability Decision，同时也是 Data Governance Decision。

### 4. Alternative approach 和 trade-off

**完全本地自治**

优点：开发速度快。

缺点：未知 MCP、Plugin 和 Permission Mode 容易产生企业 Blind Spot。

**中央 Allowlist**

优点：风险边界清楚。

缺点：新工具上线需要审批，容易降低 Experiment Velocity。

**Role-based Policy**

例如：

```text
Research team
→ broader MCP access

Production support
→ restricted write access

New employee
→ no bypass mode
```

优点：治理与创新折中。

缺点：Policy Complexity 增加。

### 5. 对 AI Systems Engineer 的启发

Agent Policy 不应该只存在于 Prompt：

```text
“不要访问不可信服务器。”
```

而应落实为 Runtime-enforced Configuration。

至少建议让 Trace 带上：

```text
organization_id
policy_version
agent_client_version
plugin_set_hash
mcp_allowlist_version
permission_mode
telemetry_policy
```

这样发生 Incident 时，才能回答：

> 当时这台机器上的 Agent **实际上被允许做什么**？

另外，一个 MCP Allowlist 也不应该只记录 URL。长期需要考虑 Server Identity、Certificate、Tool Manifest Hash、版本和 Capability Diff。

## Signal 4：Power 正成为 AI Infrastructure Scheduler 的一等资源

**Source:** NVIDIA — *Maximizing AI Factory Performance per Watt with NVIDIA DSX MaxLPS*
**Date:** 2026-08-21
**Evidence Level:** **Official**
**Technology Maturity:** **Demo**

### 1. 发生了什么

NVIDIA 本周详细介绍 DSX MaxLPS 中的 Dynamic Power Software（DPS）。DPS 目前处于 Developer Preview，它会建立从 Utility、Resource Group、Rack、Node 到 GPU 的功率拓扑，并持续采集功耗 Telemetry。

Operator 定义：

* Resource Group；
* Power Budget；
* Allocation Policy；
* Emergency Policy。

系统则在固定站点功率上限下动态移动未使用的 Headroom。([NVIDIA Developer][4])

概念上：

```text
Rack A
reserved = 100 kW
actual   = 70 kW
          │
          └─ 30 kW headroom
                    │
                    ▼
                 Rack B
```

而不是让 Rack A 的预留功率一直闲置。

### 2. 工程上改变了什么

过去 AI Scheduler 主要处理：

```text
GPU count
GPU memory
CPU
network
topology
queue
```

未来还可能加入：

```text
power_budget
thermal_headroom
performance_per_watt_profile
facility_event
grid_event
cooling_capacity
```

于是 Scheduling 目标从：

```text
maximize tokens/sec
```

进一步变成：

```text
maximize useful AI output
subject to:
    latency SLO
    power envelope
    thermal constraints
    reliability constraints
    cost
```

### 3. Architecture impact

NVIDIA 同时预览 DSX Exchange：一个连接 Compute Scheduler 与 Power Monitoring、Cooling Infrastructure、Building Management System、Grid Interface 的 IT/OT Event Bus。([NVIDIA Developer][4])

架构逐渐变成：

```text
Facility / Grid / Cooling
          │
      DSX Exchange
          │
          ▼
     Power Control
          │
  ┌───────┼────────┐
  ▼       ▼        ▼
Rack A  Rack B   Rack C
  │       │        │
  └──── Compute Scheduler
              │
          AI Workloads
```

这意味着 AI Infrastructure Control Plane 开始跨越传统 DevOps 与 Facilities / OT 边界。

### 4. Alternative approach 和 trade-off

| 方案                               | 优点        | 局限                            |
| -------------------------------- | --------- | ----------------------------- |
| Static worst-case provisioning   | 简单、安全边界清晰 | 大量 Headroom 闲置                |
| Per-GPU static power cap         | 易实施       | 不理解 Fleet 级负载                 |
| Application tuning only          | 无设施依赖     | 无法利用跨 Rack Headroom           |
| Dynamic fleet power control      | 利用率高      | Control Loop、故障和 Telemetry 复杂 |
| Scheduler + Facility integration | 全局优化      | IT/OT Security 与稳定性要求高        |

动态 Power Control 还会引入 Control Systems 问题：

* Telemetry Delay；
* Oscillation；
* Correlated Load Burst；
* Emergency Override；
* Fail-safe State；
* Control Plane Loss；
* Stale Power Budget。

这与普通 Kubernetes Resource Scheduler 已经不是同一个复杂度层级。

### 5. 对 AI Systems Engineer 的启发

未来做大规模 Training / Serving Capacity Planning，应该开始熟悉：

```text
tokens / second / watt
tokens / joule
SLO under power cap
rack power variance
thermal headroom
facility power event response
```

NVIDIA 报告在其代表性 Workload 上，GB200 / Vera Rubin 系统通过 MaxLPS 获得约 1.3–1.5× Performance/Watt，并宣称固定设施功率下可提高可部署 Rack 数；这些都是厂商在特定硬件与 Workload 上的结果，不能视为通用 Benchmark。更可靠的工程实践反而是 NVIDIA 自己建议的验证方法：拿 **Static Baseline 与 Managed Run** 对比，同时追踪 Throughput、Latency、Service Error Rate、Power Draw、Utilization 与 Policy Compliance。([NVIDIA Developer][4])

## Signal 5：Evaluation 从 LLM Judge 走向 Frozen Artifact + Temporal Outcome

**Source:** Hui Mao — *Historical Backtesting for Scientific Question Discovery: A Protocol and Astronomy Pilot*
**Date:** 2026-08-17
**Evidence Level:** **Reproducible Engineering Practice**
**Technology Maturity:** **Open Source Experiment**

### 1. 发生了什么

论文针对“AI 是否能提出好的科学问题”提出一个很有价值的 Evaluation Protocol：

```text
Historical corpus up to T0
        │
        ▼
AI generates questions
        │
        ▼
Freeze outputs
        │
        │ no future data access
        ▼
Future corpus T1...Tn
        │
        ▼
Did reality / literature
later support, answer,
refute, or independently
discover the question?
```

也就是说：

> 不让今天的 Judge 猜这个 Idea 将来有没有价值，而是让未来事实真正评分。

作者还冻结了 2026-08-17 生成的 200 个问题，计划在 2027–2030 年用未来文献进行污染-free 的 Prospective Evaluation。([arXiv][5])

### 2. 工程上改变了什么

很多 Agent Evaluation 当前是：

```text
Agent Output
     │
     ▼
LLM Judge
     │
score = 0.82
```

这种方法很方便，但它混合了：

* Judge Bias；
* Model Family Correlation；
* Prompt Framing；
* Rubric Ambiguity；
* Knowledge Leakage。

论文的一个值得重视的发现是：

* 两位认真 Human Annotator 的 κ 只有约 0.17；
* Judge Model 与专业标注者的一致性约 0.17–0.26；
* Frontier Judge Model 彼此却能达到约 0.60。

也就是说：

> **Models agree with models** 并不意味着这个 Evaluation Taxonomy 本身可靠。

([arXiv][5])

### 3. Architecture impact

长期 Agent Eval 平台可能需要增加一种新的数据类型：

```text
Evaluation Artifact
├── generation_timestamp
├── cutoff_manifest
├── allowed_sources
├── model_version
├── harness_version
├── frozen_output
├── artifact_hash
├── future_evidence_window
└── adjudication
```

这实际上把 Evaluation 从：

```text
score function
```

升级成：

```text
evidence lifecycle
```

尤其适合评估：

* Research Agent；
* Forecasting Agent；
* Investment Research；
* Incident Prevention；
* Product Idea Generation；
* Long-term Planning；
* Scientific Hypothesis Generation。

### 4. Alternative approach 和 trade-off

| Eval 方法                 | 优点          | 问题                      |
| ----------------------- | ----------- | ----------------------- |
| LLM-as-Judge            | 快、便宜、规模化    | Bias / Correlated Error |
| Expert Review           | 质量高         | 贵、慢、主观                  |
| Executable Test         | 最可靠         | 只适合有 Oracle 的任务         |
| Live A/B                | 最接近真实行为     | Deployment Risk、时间长     |
| Historical Backtest     | 有真实 Outcome | 数据泄漏与历史可重构性要求高          |
| Prospective Frozen Eval | 污染最小        | 必须等待真实未来结果              |

### 5. 对 AI Systems Engineer 的启发

以后设计长期 Agent Evaluation，最好区分：

```text
Immediate Proxy Metric
vs
Eventual Outcome Metric
```

例如：

```text
Incident Agent
Immediate:
    reviewer score

Later:
    escaped incident?
    recurrence?
    mean time to recovery?

Code Agent
Immediate:
    tests pass

Later:
    revert?
    bug introduced?
    maintenance cost?

Research Agent
Immediate:
    novelty judge

Later:
    evidence emerged?
    hypothesis refuted?
```

不是所有任务都能等待几年，但可以开始建立 **Frozen Prediction / Artifact Ledger**。

这是一个很可能被低估的 Evaluation 基础设施方向。

## Reading Guide

### 第一阶段：先理解为什么 Harnessed RL 与普通 Agentic RL 不一样

优先读：

* **1 Introduction**
* **2.1 Retokenization and Sample Merging**
* **2.2 Advantage Calculation**
* **2.3 Loss Normalization**

重点回答三个问题：

**为什么一个 Rollout 不再等于一个 Training Sequence？**

Harness 可能 Summary、Spawn Sub-agent 或重建 Prompt，因此一个 Task Rollout 会产生多个 Model Call 和 Training Sample。([arXiv][6])

**为什么不能把上一轮 Response Decode 成字符串后重新 Tokenize，再假装还是同一个 Token Sequence？**

因为：

```text
Tok(Decode(tokens))
≠
tokens
```

在某些 Token Boundary 上可能发生变化；Chat Template 和 Tool-call Serializer 也可能改变原文本。论文指出，如果为了提高 Prefix Merge Rate，把旧 Token 强行拼回新 Prompt，可能导致实际 Training Prompt 与 Rollout 时模型真正看到的 Prompt 不一致，从而产生 Off-policy Stitching。([arXiv][6])

**为什么 Sample Count 不能决定一个 Rollout 的统计权重？**

因为 Sample Count 可能只是 Harness Implementation Detail。一个 Rollout 因 Context Summary 变成四段，不应该因此获得四倍权重。([arXiv][6])

## Engineering Extraction

读完以后，建议确保自己能够解释以下六件事：

### 1. Agent Rollout 与 Training Sample 为什么不是一对一

```text
1 business task
→ N model calls
→ M training sequences
```

Harness 内部操作会改变 `M`。

### 2. 为什么必须保存 exact sampled tokens / exact consumed prompt

不能只保存：

```text
messages.json
```

因为训练需要知道模型当时真正 condition 在什么 Token Sequence 上。

### 3. 为什么 Rollout ID 是统计语义，不只是 Trace ID

如果 flatten 后丢掉 `rollout_id`，Loss Normalization 和 Advantage Calculation 都可能错误。

### 4. 为什么 Control Plane 要 Idempotent

Trainer、Gateway、K8s Controller 都会独立失败和重试。

```text
retry
≠
new rollout
```

### 5. 为什么 Training Environment 必须被版本化

Agent Training 的 Reward 取决于：

* Repo Snapshot；
* Tests；
* Network；
* Tool；
* Sandbox；
* Harness。

Environment 改变就是 Reward Function 改变。

### 6. 为什么 Train / Eval / Deploy 应尽量共享 Harness

否则模型学习的是：

> simplified training world

而上线后遇到：

> real harness world。

## Practical Experiment：验证“一个 Rollout ≠ 一个 Sample”

**时间：约 1.5–2.5 小时；不需要训练模型，也不需要 GPU。**

### 目标

亲手验证两个问题：

1. Harness 的内部行为为什么会改变一个 Rollout 产生的 Sample 数；
2. 如果错误地按 Sample 做统计，会怎样改变 Rollout 的权重。

### Step 1：构造 100 个虚拟 Rollout

每个 Task 返回：

```python
{
    "rollout_id": "...",
    "reward": 0 | 1,
    "samples": [...]
}
```

让：

* 成功 Rollout 平均生成 3 个 Sample；
* 失败 Rollout 平均生成 1 个 Sample。

这可以模拟更长的成功 Agent Workflow，或有 Sub-agent / Summary 的任务。

### Step 2：计算两种 Reward Mean

**错误方式：Sample-level**

```text
reward copied to every sample
mean over all samples
```

**正确对照：Rollout-level**

```text
mean reward over rollouts
```

你会看到，只要 Sample Count 与 Outcome 有相关性，两者就会产生系统性偏差。

### Step 3：模拟 Harness Split

定义：

```text
Call 1:
prompt A
response X

Call 2:
prompt A + X + tool result
response Y
```

然后在第二次 Prompt 中人为插入：

* Context Summary；
* Chat Template 差异；
* 空格规范化；
* Structured Tool Result Re-serialization。

记录：

```text
text-prefix-match
token-prefix-match
```

观察文本看起来“相同”的历史为什么不一定在 Token 层完全可拼接。

### Step 4：加入一次 Duplicate Request

模拟：

```text
POST /model-call
→ network timeout
→ client retry
```

为 Request 设置：

```text
rollout_id
attempt_id
request_fingerprint
```

验证第二次请求是否能被 Deduplicate。

### Step 5：记录最小 Event Log

```text
RolloutCreated
AgentStarted
ModelRequested
ModelResponded
ToolCalled
ContextCompacted
ModelRequested
RewardAssigned
RolloutCompleted
```

要求任何 Event 都可以通过 `rollout_id` 重建 Task Lifecycle。

### 验证方式

实验完成后，至少应该证明：

| 问题                             | 预期结果                    |
| ------------------------------ | ----------------------- |
| Sample-level reward statistics | 被 Sample Count 偏置       |
| Rollout-level statistics       | 保持 Task 权重一致            |
| Text prefix                    | 不保证 Token prefix        |
| Duplicate API request          | 不产生第二份 Model Call       |
| Context summary                | 一个 Rollout 可以拆成多 Sample |
| Event replay                   | 可以重建 Rollout Lifecycle  |

如果这几个现象能够在几十行模拟代码里重现，那么论文最重要的 Systems Insight 就已经理解了。

# 5. Noise Filter

## “Open-source Harness 出现了，所以 Agent Harness 已经标准化”

没有。

Codex `app-server` 是一个具体 Harness Protocol，而不同 Agent System 对：

* Context；
* Tool；
* Approval；
* Compaction；
* Handoff；
* Event；

仍有不同语义。([BERJAYA][1])

目前更准确的判断是：

> **Harness 已成为稳定问题域，而不是已经有统一标准。**

---

## “Agents in Dev, Artifacts in Prod 就天然安全”

不成立。

静态 Artifact 仍然可能包含：

* 错误 IAM；
* 数据泄漏；
* 错误 SQL；
* 不正确 Retention；
* 不可逆 Migration。

它只是把风险从：

```text
runtime nondeterminism
```

转化成：

```text
build-time validation problem
```

因此真正价值来自：

```text
Generate
→ Static Analysis
→ Test
→ Policy Check
→ Review
→ Promotion
```

而不是“没有 Runtime LLM”本身。([Amazon Web Services, Inc.][2])

---

## “开 OTel 就拥有 Agent Observability”

不成立。

Managed OTel 解决的是数据可以统一送到哪里，不自动解决：

* Span Semantics；
* Agent Run Correlation；
* Tool Call Identity；
* Artifact Provenance；
* Context Version；
* Approval Event；
* Secret Redaction。

GitHub甚至专门把 Content Capture Policy 做成企业配置，本身就说明 Telemetry 内容可能存在治理风险。([The GitHub Blog][3])

---

## “NVIDIA 的 1.5× Performance/Watt 可以当行业普遍收益”

不能。

这些数字来自 NVIDIA 自己在特定硬件、模型与配置上的 Representative Workload。([NVIDIA Developer][4])

应该保留的信号是：

> Power 正从静态 Facility Capacity 变成可动态调度资源。

而不是具体提升倍率。

---

## “多个 LLM Judge 互相同意，所以评价可信”

本周 Historical Backtesting 论文恰好提供反例：Frontier Judge Model 彼此之间一致性很高，但与专业人类标注的一致性显著低得多。([arXiv][5])

因此：

```text
Inter-model agreement
≠
Ground-truth validity
```

尤其是多个模型共享相似训练数据、Bias 或 Rubric Interpretation 时。

---

## “Harness RL 提高 14.6 个百分点，所以 Harnessed RL 已经成熟”

也不能这么推导。

Agent Lightning 的 Qwen3.5-9B SWE-bench 结果来自作者自己的特定 Dataset Cleaning、Environment 和训练流程。([arXiv][6])

本周真正成熟的是**问题定义**：

> 真实 Harness 进入训练后，Token Provenance、Rollout Weight、Idempotency 和 Scheduler 都必须重新设计。

算法最优解仍未定型。

# 6. Engineering Practice Signals

| 本周来源                       | 值得直接吸收的工程实践                                                                                                                                           |
| -------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Agent Lightning**        | 所有 Sample 即使 Flatten 成 Tensor Batch，也保留 `rollout_id` 与 Prompt Group Provenance；不要让 Harness 内部 Sample 数改变 Task 的统计权重。([arXiv][6])                      |
| **Agent Lightning**        | Gateway、Controller、Trainer 是独立 Failure Domain 时，Control-plane API 必须 Idempotent；重试 Model Request 需要 Deduplication。([arXiv][6])                        |
| **Agent Lightning**        | Agent Execution 可以使用普通 Kubernetes Job；Environment、Network Policy 和 Reward Harness 应一同版本化。([arXiv][6])                                                 |
| **Agent Lightning**        | Coding Agent 训练前先清理 Environment Dataset；论文发现大量空 Problem Statement、缺失 Branch 等问题，说明 Environment Corruption 会直接变成 Reward Noise。([arXiv][6])             |
| **AWS ADOP**               | 将模型输出先落为 Static Artifact，再走 CI/CD；对存在可靠 Validator 的 Workflow，优先避免让 LLM 成为生产 Critical Path。([Amazon Web Services, Inc.][2])                            |
| **AWS ADOP**               | Agent Trace 至少记录 Intent、Tool、Outcome 和 Cost，并允许发送到 OTel；但 Production Artifact 与 Agent Trace 应分开治理。([Amazon Web Services, Inc.][2])                    |
| **GitHub Copilot**         | 企业 MCP 应采用 Central Allow/Deny Policy，而不是依赖开发者自己维护可信服务器列表；Managed Policy 应覆盖 Override / Bypass 模式。([The GitHub Blog][3])                               |
| **GitHub Copilot**         | OTel Collector、Resource Attributes 与 Content Capture Policy 一起管理；Observability 配置必须同时考虑 Privacy / Secret Exposure。([The GitHub Blog][3])              |
| **NVIDIA MaxLPS**          | Power Optimization 评估不要只看瓦数；比较 Static 与 Managed Run 时同时记录 Throughput、Latency、Error Rate、Power、Utilization 和 Policy Compliance。([NVIDIA Developer][4]) |
| **Historical Backtesting** | 对长期结论保存 Frozen Output、Cutoff Date、Allowed Corpus 与 Artifact Hash；以后获得真实 Outcome 时再 Join，而不是事后重新生成。([arXiv][5])                                        |
| **OpenAI Daybreak**        | 长时间 Agent Scan 应保存阶段、已检查文件、Worker 状态与 Token Usage；中断后从已完成工作恢复，而不是整个任务重跑。([BERJAYA][9])                                                                |
| **OpenAI Daybreak**        | AI 安全分析不要替换现有 Static Scanner；更合理的是把已有 Scanner Alert 作为 Queue，再由 Agent 做上下文验证、攻击路径分析和 Evidence 收集。([BERJAYA][9])                                       |

OpenAI 本周 Daybreak 的工程细节尤其值得作为 **Production Reliability 补充信号**：长时间 Deep Scan 可以在中断后 Resume，而不用重复已经完成的工作；系统显示 Reviewed Files、Active Workers、Elapsed Time 与 Measured Token Usage，并把 Evidence、Attack Path、Confidence 与 Coverage 暴露给 Reviewer。([BERJAYA][9])

这说明一个 Agent Workflow 真正进入生产后，工程重点最终会落到非常传统的问题：

```text
Checkpoint
Resume
Idempotency
Artifact Persistence
Partial Completion
Cost Budget
Evidence
Human Review
```

而不是“Agent 能不能一次做完”。

```text
                        │
                        ▼
                 Evidence Plane
              Trace / Eval / Outcome
```

我认为本周最值得长期积累的不是某一个 SDK，而是下面五类能力：

1. **Harness Semantics**：Context、Tool、Approval、Recovery 到底属于谁。
2. **Probabilistic-to-Deterministic Boundary**：什么时候应该生成 Artifact，而不是让 Agent 永久在线。
3. **Endpoint Governance**：Local Agent 的 Tool、MCP、Plugin 和 Telemetry 如何由组织治理。
4. **Resource-aware Control Plane**：除了 GPU、Memory、Queue，开始理解 Power、Thermal 与 Facility Constraint。
5. **Evaluation Provenance**：不仅得到一个 Score，而是保存能够几年后重新证明结论的 Evidence Lifecycle。

其中最重要的长期判断是：

> **随着模型能力继续提高，AI Systems Engineer 的价值反而越来越集中在“模型之外”：定义 Harness、状态、资源、权限、验证和证据的系统语义。**

这些问题不会因为下一代模型更聪明而消失。恰恰相反，Agent 能运行得越久、调用的工具越多、触及的系统越真实，这些边界就越重要。
